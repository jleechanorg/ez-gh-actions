## 1. Goal

Deliver, for the four items in bd-dea.10:

- (a) a change that reduces crash probability,
- (b) logging that attributes the next crash to "kernel use-after-free" or "degraded CPU",
- (c) a decision on `kernel.panic_on_oops`,
- (d) one discriminating experiment and a `soakctl` protocol, changing one probability-affecting variable at a time.

Done means: the next crash produces a vmcore that a written triage procedure classifies as CONTROL-FLOW-MISMATCH, BAD-TARGET-CONSUMED, UAF-SUPPORTED, or INCONCLUSIVE (§ 5), and the box either survives 400 h under the experiment or the cross-dump conclusion selects the next single-variable step. Criteria are in § 10.

## 3. Problem statement

Two hypotheses survive the four lanes:

- **H-SW (kernel use-after-free in scheduler/cgroup teardown under runner churn).** For: E1 (deterministic small fault addresses, 0x283 ×9), E2 (#26 lands on the runner thread right after veth teardown), E11 (churn is high), upstream PSI/EEVDF fixes (upstream_research.md § Q1). Against: 6d22h survival with `cgroup_disable=cpu` ended in the same code path with no cgroup cfs_rqs (history_summary.md § (b) item 10).
- **H-HW (Raptor Lake Vmin-shift on the favored cores).** For: E3 (26/26 on the two highest-V/f cores), E5 (253 W sustained), history_summary.md § (c) (memtest, C-state, microcode rollback never completed). Against: E6 (0x133 is post-0x12F), no MCE/EDAC/AER-fatal evidence (hardware_evidence.md § Verdict), and E21: the favored cores are also where the scheduler steers work (ITMT), so clustering alone cannot separate the two hypotheses.

Neither hypothesis is falsifiable from pstore text. A vmcore is: it shows whether the memory the CPU should have read still holds a valid value (CPU mis-executed → H-HW) or holds the garbage the CPU used (memory corrupted → H-SW or DRAM). Every design choice below preserves that vmcore.

## 4. Decisions

### D1 — Probability reduction: restore Intel default PL1, then cap the two favored cores to the common 5.5 GHz bin (one combined H-HW mitigation)

Set `scaling_max_freq=5500000` on cpu0–3 (runtime, sysfs, reverts in seconds, no reboot, no fleet impact). The cap is non-increasing: a core whose limit is already below 5.5 GHz keeps it, and `assert` treats at-or-below the cap as capped. Rationale:

1. It is the only lever that directly tests E3, the strongest statistical anomaly in the corpus.
2. It keeps ITMT priority unchanged (priority derives from HWP highest-perf, not from `scaling_max_freq`), so scheduler steering toward cpu0–3 is constant and only the V/f point moves. It probes only one H-HW variant: the light-load top-turbo bin, which is exactly the state of an idle favored core woken by a softirq (24/26 crashes). It does not probe the idle/C-state exit-voltage variant; that is S2e (persistent `intel_idle.max_cstate=1`, bd-qy1). If crashes continue on cpu0–3 at 5.5 GHz, only the top-bin variant loses; if they stop for 400 h, H-HW gains strongly. The vmcore, not the cap, is the primary discriminator (§ 5).
3. Prior worth stating: nine identical `0x283` fault addresses (E1) are easier to explain by a stale field read through a freed pointer than by mis-execution, so the software hypothesis starts ahead. The cap is chosen because it is the cheapest reversible H-HW probe, not because H-HW is favoured.
4. **Damage containment precedes the experiment.** Intel's Raptor Lake guidance is BIOS with microcode ≥ 0x12F **and** Intel Default Settings (13900K: PL1 = 125 W, PL2 = 253 W). The board runs PL1 = PL2 = 253 W (E5), so it is not on Intel defaults. Restoring PL1 = 125 W (leave TVB and PL2 alone) happens in window W before S1 (W1b), because a 400 h soak must not deliberately keep an aging-accelerating power profile for the sake of attribution purity. S1 is therefore a **combined H-HW mitigation** (PL1 restore + cap), not a cap experiment: a clean S1 supports H-HW as a class and says nothing about the cap alone; the handoff permits two changes when the vmcore attributes, and neither change alters the software hypothesis. Attribution between the two comes only from the S3 reverse test (remove the cap at PL1 = 125 W); a no-cap baseline at PL1 = 125 W before S1 was rejected because it would spend a 200 h soak on the weaker single change while damage may continue.
5. Cost of the cap: ≤5 % single-thread peak on two cores; runners are 2-CPU-quota containers and all-core turbo is already ≤5.5 GHz, so the cap alone does not change CI throughput. The PL1 restore (item 4) does have a throughput cost under sustained all-core load; it is quantified in § 7.

### D2 — Logging

1. **Keep kdump** (E7) and **raise the reservation before the proof**: `kdump-config` recommends 1252 M against 640 MiB reserved, and Ubuntu's kdump documentation says an undersized crash kernel can OOM. Set `crashkernel=1536M,high crashkernel=128M,low` in `/etc/default/grub.d/kdump-tools.cfg` in window W0, take effect on the W1 reboot, verify `kexec_crash_size` ≥ 1.5 GiB before W3. Not a probability-affecting variable (§ 7).
2. **Lockup panics:** `kernel.softlockup_panic=1`, `kernel.hardlockup_panic=1`, `kernel.hung_task_panic=0` (unchanged), via `/etc/sysctl.d/90-jeff-ubuntu-crash-capture.conf` (owned by user_scope, E19/E20). A freeze without an oops then panics into kdump instead of hanging until a human power-cycles. Blast radius in § 7.
3. **`kernel.panic=10`:** after a panic the box reboots itself in 10 s if the crash kernel did not take over. This is a requested operator exception to the CLAUDE.md prohibition, argued in § 8; it is not claimed to be compliant.
4. **netconsole → MacBook** over the idle wired NIC. The kernel documents `src-ip` as an interface address, so the loader unit adds `192.168.254.130/32` to `eno2` (a host route only; no connected `/24`). Because the host runs `arp_ignore=0`/`arp_announce=0` (live `sysctl net.ipv4.conf.all.arp_ignore`), a second NIC on the same segment would answer ARP for the Wi-Fi address and flap the router's entry, moving fleet traffic onto the igc NIC and changing softirq load mid-soak; the unit therefore sets `net.ipv4.conf.eno2.arp_ignore=1`, `net.ipv4.conf.eno2.arp_announce=2` and `net.ipv4.conf.wlp0s20f3.arp_ignore=1` before adding the address, and sets the link up before `modprobe netconsole`. The unit reads `/etc/default/netconsole-eno2` (`EnvironmentFile=-`) so `NETCONSOLE_TGT_MAC` has a home, and its `stop` mode unloads the module, deletes the `/32` and restores the ARP sysctls to the host default (0) so nothing lingers after the soak. A `/dev/kmsg` probe proves ordinary transmission only; C7 is met only when the MacBook log also contains the W3 SysRq panic line (panic-context netpoll delivery). The target MAC defaults to broadcast (the MacBook's Wi-Fi MAC `ae:2f:…` is a locally administered, possibly rotating private address); because switches may suppress broadcast, the unit accepts an explicit `NETCONSOLE_TGT_MAC` and T4 records which mode delivered. The unit is ordered after `sys-subsystem-net-devices-eno2.device`, never `modules-load.d`. Receiver: a launchd job on the MacBook running `nc -ukl 6666`. Value: last minute of kernel log before a crash and a backup if kdump fails; gap: MacBook sleep loses packets (accepted). netpoll works on NAPI drivers without `ndo_poll_controller`; T3/T4 prove it with a live `/dev/kmsg` probe before the item is marked done.
5. **vmcore triage script** (`scripts/vmcore-triage.sh` in user_scope) that runs `crash` in batch against a dbgsym `vmlinux` and prints the register-versus-memory comparison that decides § 5.

### D3 — `panic_on_oops`: keep 1

`kdump-config` forces it (nextsteps § Executive summary). On this host an oops has never been survivable (E9: zero `Oops:` lines in the retained journal, 26 boots ended by an oops), and every oops was in scheduler core, where continuing means running on freed `rq` state. Overriding it after `kdump-tools` starts would trade the only artifact that can settle H-SW vs H-HW for an unmeasurable chance of limping on. Decision: keep `kernel.panic_on_oops=1` and state it explicitly in the same sysctl file so a future `kdump-tools` change cannot silently flip it.

**Variables.** Logging changes (D2) do not alter crash probability. S1 applies two probability-affecting changes on the same hardware side (PL1 restore as damage containment, then the cap), so S1 is a combined H-HW mitigation (D1.5); the software hypothesis is untouched and the vmcore attributes any crash regardless. The S3 reverse test separates the two.

## 5. Vmcore triage decision procedure

Inputs: `/var/crash/<ts>/dump.<ts>`, `vmlinux` from the matching dbgsym ddeb whose Build ID equals the running kernel's (W0a). `scripts/vmcore-triage.sh` prints, in order: `sys`, `log | tail -120`, `bt` (for the panic task `crash` prints the exception frame's saved registers inline: `[exception RIP: …]` followed by `RIP/RSP/RAX…`), `bt -e` (locates every exception frame on the stack), `bt -f` (frame contents), the disassembly ending at the return address of the **first frame printed after the `[exception RIP:` block** (for the panicking task `bt` numbers the panic machinery first: `#0 machine_kexec`, `#1 __crash_kexec`, …, so "frame #1" is the wrong frame; the caller whose return address follows the call that reached the bad `RIP` is the first frame after the exception block), `rd -x` of every memory word that instruction or its feeding `mov` reads, `kmem` for the bad `RIP` and for the fault address, `kmem -s` filtered to scheduler/cgroup/PSI caches, `ps -A | head`, `runq`. The script never classifies; it emits `VERDICT: INCONCLUSIVE reason=human-review-required` (or `sysrq-induced`) and the evidence path.

**What a vmcore can and cannot say.** Registers in the exception frame (`bt`'s `[exception RIP: …]` block; note `bt -r` is raw stack data, not registers) were captured at the exception instant; dump memory was captured later, after the crash NMI stopped the other CPUs, so a concurrent free-and-reuse can rewrite a word in between. More fundamentally, a degraded core can corrupt the *load* that filled the branch register, an address calculation, a cache line, or an earlier store, so "the register already held the bad value" locates where corruption became architecturally visible; it does not say whether software or silicon put it there. The taxonomy below is therefore evidential, not causal, and the only strong single-dump signal is a reconstructed transfer whose contemporaneous source was valid while `RIP` was not.

**Step 1 — reconstruct the transfer** from `dis -r <return address of the first frame after the exception block>`. `dis -r ADDR` disassembles from the routine start up to and including ADDR, so the last line is the instruction at the saved return PC and the transfer (call/jmp) is the line immediately before it. The heuristic holds when the exception RIP is not a valid text address (this host's class). When `[exception RIP:` resolves to a real symbol, the faulting instruction is at the exception RIP and the script disassembles up to and including it; which function the first post-exception frame belongs to is not asserted (in `crash`'s x86_64 `bt` it is often still the caller, from the return address at the exception RSP) and is confirmed by hand. The script prints `frame_source=` (`first-frame-after-exception-block`, `exception-rip-is-a-valid-symbol:disassembling-to-the-faulting-instruction`, or `fallback-frame-1-verify-manually`); anything but the first is confirmed by hand; Ubuntu 6.17 compiles C indirect calls to `call __x86_indirect_thunk_<reg>` and `sched_clock` goes through a static-call trampoline, so the apparent form must be resolved to its real source:

| Instruction form | Branch-target source |
|---|---|
| `call *%reg` or `call __x86_indirect_thunk_<reg>` | the named register in the exception frame printed by `bt` (confirm the thunk did not clobber it: `dis __x86_indirect_thunk_<reg>`) |
| `call *disp(%reg)` | the memory word at `reg+disp`, read with `rd -x` (dump-time value; may have changed) |
| `call <symbol>` to a real function | the rel32 immediate in the text page, re-read with `rd -x` at the call site |
| `call __SCT__*` (static call) | the trampoline's `jmp` target: `dis __SCT__<name>` |
| `ret` (the exception frame is not reachable from the caller frame's call) | the stack slot shown by `bt -f` |

If the unwinder output is inconsistent (the caller frame's return address does not sit after a transfer instruction, or the stack shows a later indirect transfer inside the callee), stop at INCONCLUSIVE.

**Step 2 — classify the single dump:**

| Class | Rule |
|---|---|
| CONTROL-FLOW-MISMATCH | Transfer reconstructed unambiguously; its contemporaneous source (an exception-frame register, an intact text immediate, or an intact static-call trampoline) holds a **valid kernel text address** and `RIP` differs. Evidence that the core did not execute what it was given, with one caveat that keeps it short of proof: the exception frame is itself kernel memory (`pt_regs` saved on the stack at entry), so a memory-corruption defect can also produce an apparently valid source next to a bad `RIP`. Record the CPU number (E3 predicts 0–3). |
| BAD-TARGET-CONSUMED | The contemporaneous source **holds the bad value** (0x283, 0x0, or the freed-page address). Establishes where corruption became visible; origin undecided. |
| UAF-SUPPORTED | BAD-TARGET-CONSUMED **plus** an independently demonstrated object-lifetime violation: the word lives in an object of a scheduler/cgroup/PSI cache (`kmem`), that object's owner is gone (its cgroup/task_group/psi_group is not reachable from live lists), the allocator state shows free or re-use, and the pre-crash log shows the matching cgroup teardown (veth/scope removal) within seconds. "Address is inside a slab page" alone does not qualify. |
| INCONCLUSIVE | Everything else: `crash` cannot load the dump; the transfer cannot be reconstructed; the source is memory-only and its dump-time value is valid (unprovable either way); the register was clobbered by the thunk; the unwinder disagrees with itself. Record the exact gap and continue the soak. |

**Step 3 — cross-dump conclusions** (these, not single dumps, drive S2 decisions):

- HARDWARE-SUPPORTED: two independent CONTROL-FLOW-MISMATCH dumps **and** at least one piece of **CPU-specific** evidence that does not come from a vmcore: a decoded MCE whose bank is a core/cache bank on cpu0–3 (`ras-mc-ctl --errors` or `rasdaemon` journal, not the mere presence of a latch), an Intel Processor Diagnostic Tool FAIL, or the S3 reverse test bringing the crash back on cpu0–3. A memtest error is **not** corroboration: it names a third cause (DRAM/IMC) and is already a hard stop at W1 that routes to the RAM path. Mismatch dumps alone, however many, never open S2c, because the saved frame they rely on is memory too.
- SOFTWARE-SUPPORTED: two UAF-SUPPORTED dumps, or one UAF-SUPPORTED dump whose lifetime violation matches a named upstream fix (upstream_research.md § Q1).
- Anything less stays open; the soak continues and the next single-variable step is chosen from the S1 outcome table, not from the class label.

A second reviewer (Codex) re-reads every report before a class is recorded in bd-dea.10 (C12), and no S2c (BIOS/RMA) action opens on a single dump.

## 8. Safety principles — requested exception, not compliance

CLAUDE.md § Safety & Monitoring Principles forbids any script, daemon, test, or automation in ez-gh-actions from invoking **or instructing** host reboot, forced-panic, or SysRq primitives, and `tests/forbid_host_reboot_primitives_test.sh` enforces it for active code (E19). This design asks the operator to grant a bounded exception for three host-level settings and one supervised action:

1. `kernel.softlockup_panic=1`, `kernel.hardlockup_panic=1` — turn a frozen host into a captured panic. Never observed to fire here (E9).
2. `kernel.panic=10` — bounds how long a panicked host stays dead if kdump does not take over; `kdump-tools` already reboots after a successful dump.
3. One SysRq-c capture proof (W3), operator-run, drained, watched, never scheduled.

Why the exception is worth asking for: without 1–3 the Sep 26 crash froze the host for 78 minutes until a human arrived, and no vmcore existed; the only artifact that can end the H-SW/H-HW argument is the vmcore these settings guarantee. Why it stays bounded: none of them can fire on a healthy host (§ 7), none run on a schedule, and none give ezgha or any daemon reboot authority. The artifacts live in user_scope so that ezgha never carries host-lifecycle instructions; the ez-gh-actions test keeps passing on its own terms, and these two documents are the only place in this repo that name the settings, each marked `OPERATOR-ONLY`. Self-outage check: a capture setting can only cause an outage through a false-positive lockup (never observed) or a kdump-time failure, which W3 proves before the settings are relied on. If the operator declines P6b, D2 items 2–3 are dropped (and if P6a is declined, W3 too), `panic_on_oops` stays at kdump-config's value, and the design still proceeds with D1 and the soak; an oops still panics into kdump (`panic_on_oops` stays 1) and § 5 still runs on that vmcore, but a hang without an oops is not captured and the capture path stays unproven until the first real crash.
