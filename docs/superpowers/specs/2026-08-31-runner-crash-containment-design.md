# Runner Crash Containment Design

**Date:** 2026-08-31
**Status:** Revised after formal `/advice` review; implementation not started
**Primary goal:** Keep the physical Ubuntu host, desktop session, Warp, and operator tools responsive while ten Linux GitHub Actions runners execute concurrently.

## Problem Statement

The production fleet currently runs ten runner containers through the host Docker daemon. Each container has a finite memory, CPU, and PID limit, but the shared host `actions.slice` has infinite aggregate limits. The tracked finite `actions.slice` is installed only inside Colima, so it does not constrain host-Docker containers. At the same time, a local `agents.slice` drop-in overrides the tracked finite values with infinity, while Ubuntu's vendor `user@.service` policy monitors the entire user manager for memory pressure.

That topology inverts the intended failure order. During runner refill bursts, `systemd-oomd` can kill the deploy owner's `user@UID.service`, taking Warp, tmux, Codex, and the desktop session together, while the runner aggregate remains unbounded. Colima is not the root requirement: the availability requirement is that lower-priority workloads fail before the operator session and physical host.

## Goals

1. Keep exactly ten Linux runner slots configured and available; reducing runner count is not an accepted containment mechanism.
2. Make runner memory, CPU, swap, and process use finite in one host-level aggregate in addition to existing per-container limits.
3. Make interactive agent and automation aggregates finite so they cannot consume the host reserve.
4. Ensure runner and agent pressure is handled inside explicit workload roots while the desktop user manager is not a direct `systemd-oomd` monitoring root.
5. Refuse new runner admission when required containment is missing or infinite.
6. Keep every production control, installer, verifier, and policy statement git-tracked and portable to a fresh Ubuntu machine.
7. Preserve operator-only authority over physical-host reboot, shutdown, VM teardown, and other broad lifecycle actions.

## Non-Goals

- Containing deliberately malicious workflow code or kernel exploits. Host Docker shares the host kernel and is accepted for this trusted-workload threat model.
- Making Colima a required Linux backend.
- Adding another watchdog, polling daemon, or automatic host/VM restart loop.
- Reducing the ten-runner Linux capacity contract.
- Reworking runner registration, GitHub API reconciliation, or per-job lifecycle behavior.

## Approaches Considered

### 1. Host Docker with a fail-closed host resource envelope (recommended)

Keep the existing host Docker execution path. Add a real system-level `actions.slice`, directly enroll workload slices with `systemd-oomd`, disable broad monitoring of `user@.service`, and require a startup preflight before runner admission.

This has the fewest runtime layers, avoids QEMU overhead, and directly fixes the observed failure: unbounded workload aggregates combined with a desktop-wide OOM target. It does not provide a separate kernel security boundary, which is outside this design's threat model.

### 2. Colima-only Linux runners

Repair `/dev/kvm` boot ordering, converge the legacy and canonical Colima profiles, remove writable host-home mounts, size QEMU, and run Docker inside the VM. This provides a stronger security boundary, but QEMU remains a large host process requiring the same cgroup/OOM policy. It also introduces VM boot, disk, socket, and lifecycle failure modes that do not advance the primary crash-containment goal.

### 3. Colima primary with host-Docker fallback

Prefer Colima but silently switch to host Docker when the VM is unavailable. This is rejected. The August 27 host-Docker drop-in was created immediately after repeated Colima failures and bypassed the only tracked aggregate limit. A topology-changing fallback makes the active safety contract unknowable during an incident.

## Architecture

### Resource hierarchy

The host uses three workload aggregates with non-overlapping ownership:

```text
-.slice
├── actions.slice                 system scope, Docker container scopes
│   └── docker-*.scope            one ephemeral runner per scope
├── ezghaproof.slice              system scope, synthetic proofs only
│   ├── ezghaproof-hardlimit.slice
│   └── ezghaproof-oomd.slice
├── user.slice
│   └── user-1000.slice
│       └── user@UID.service
│           ├── agents.slice      interactive coding agents and descendants
│           ├── automation.slice  AO and factory daemons
│           ├── app.slice         Warp and desktop applications
│           └── session.slice     GNOME session services
└── system.slice                  Docker daemon and host services
```

`actions.slice` is a root-owned system slice because Docker creates container scopes through the system manager. Installing a user-scoped unit with the same name does not constrain those scopes and is forbidden as evidence of containment.

### OOM ownership

- `actions.slice`, `agents.slice`, and `automation.slice` set `ManagedOOMMemoryPressure=kill` with an explicit 50% pressure limit.
- Tracked system drop-ins force both `ManagedOOMMemoryPressure=auto` and `ManagedOOMSwap=auto` on `-.slice`, `user.slice`, the deploy owner's `user-UID.slice`, `user@UID.service`, and the desktop app/session ancestors. The broad `user@UID.service` also resets `ManagedOOMPreference=none` and `OOMScoreAdjust=0`; setting it to `omit` or assigning a negative score is forbidden because that protects the entire session subtree and can displace kernel/oomd victims rather than containing the source. `ManagedOOMMemoryPressureLimit=0%` is not treated as protection because systemd ignores that property unless pressure mode is `kill`. This explicitly removes the vendor `user@UID.service` kill target that formed the previous crash blast radius: Warp, tmux, Codex, and the desktop manager must not be selected as one unit. Only finite workload roots (`actions.slice`, `agents.slice`, and `automation.slice`, plus an active proof root) may appear as `systemd-oomd` kill roots in `oomctl`.
- Hard `MemoryMax` limits remain the deterministic last boundary even if `systemd-oomd` is unavailable or slow.
- No workload receives `OOMScoreAdjust=-1000`. Protected workload exemptions invert the intended kill order and are removed from the host-Docker topology.
- Supported agent launchers have no environment escape hatch around `agents.slice`; every detected supported agent CLI process must be a descendant of the finite aggregate before deployment proceeds. Existing unscoped processes are reported and allowed to exit or be relaunched, never killed automatically.
- Independent monitored roots have no global priority order. The contract is local: an `actions.slice` pressure action chooses an eligible runner descendant, while agent and automation pressure is handled inside their own roots.
- `MemorySwapMax=0` prevents runner swap thrash but can make pressure rise faster than `systemd-oomd` reacts. Kernel hard limits are therefore the final containment mechanism, not a claim of deterministic oomd timing.

### Admission permit

Rust owns a short-lived opaque `AdmissionPermit` through one canonical containment implementation. `ezgha containment-check --install-static --json` exposes a read-only verdict for the mode-`0600` proposed endpoint, hardware, deployment state, privilege, current use where applicable, and rollback storage without requiring a reachable VM daemon. For an explicitly configured recoverable Colima/Lima endpoint only, that verdict may authorize the separate exact-backend recovery decision. `ezgha containment-check --install-dynamic --json` then exposes a read-only verdict for reachable endpoint topology, Docker's cgroup driver, and `oomctl`; both install verdicts must pass before image work but neither returns an admission capability. `--admission` exposes the stricter runtime verdict after effective installed cgroup/oomd policy and every final deployment-receipt artifact pass. Internal Rust callers use that same implementation to obtain an in-memory permit with a private scope and expiry. `RuntimeAdmission` authorizes only the established runtime mutation paths after final installed-state validation. Private `TransactionAdmission` is callable only by deferred service installation with a validated inherited transaction-lock FD and candidate directory; it validates every non-unit receipt artifact at its final path and both unit candidates at their receipt-bound staged paths, and authorizes only atomic installation, verification, and manager reload for those two units. It cannot reach service start, pre-pull, reconciliation, registration, or runner creation. The CLI JSON never serializes or accepts either permit, so an environment variable, CLI argument, or shell-generated JSON cannot forge one.

Every Linux runner-admission-side mutation requires a scoped permit immediately before admission: direct `start`, direct `serve` before pre-pull, and every `ensure_count` reconciliation tick. Direct `install-service` also requires runtime admission. Direct commands perform the full bounded check synchronously. Long-lived `serve` performs one full check before pre-pull, then owns an `AttestationSupervisor` with exactly one read-only full check in flight. A new run starts no later than 20 seconds after the preceding completed run and has a 15-second wall-clock deadline including child processes. It checks Docker, `systemctl`, `oomctl`, config, receipt, SHA-256 digests, endpoint/topology, fixed count, cgroup state, and policy, then atomically publishes a non-capability `RuntimeAttestation` containing pass/failure class, monotonically increasing generation, completion instant, boot ID, normalized endpoint, persisted count, and receipt/config metadata identities. A successful snapshot expires 45 seconds after completion. The reconciliation thread never invokes or joins those probes and never charges them to its 30-second cadence or the shared 75-second queue-monitor budget.

Each runner-creating tick mints a distinct in-memory `TickAdmission` after a subprocess-free fast guard atomically reads the current snapshot and rechecks boot ID, persisted endpoint/count, and receipt/config metadata identity. The guard performs no Docker, GitHub, systemctl, `oomctl`, or SHA operation and has a live p99 budget of 100 ms. A permit records the attestation generation and expires at the earlier of 30 seconds after issue or snapshot expiry. It is type-required by `ensure_count` and each runner-creating transition. Cleanup may proceed without it, but `assert_current()` must pass immediately before slot reservation, JIT registration, and container creation. A newly published generation/failure revokes older permits, so drift discovered between two starts blocks the second.

A shared `AdmissionControl` atomically publishes `Healthy`, `StaleSince(t)`, or `PolicyFailed` and wakes/cancels foreground work when the state worsens. `serve` checks it at the top of every loop iteration, including settle and monitor iterations, before and after every bounded external operation, and inside every wait loop at least once per second. Serve-mode child processes must be cancellable through that token; one-shot network/system calls have hard deadlines of at most 15 seconds. A completed permanent policy failure revokes all permits, emits one cooldown-deduplicated critical containment alert with evidence class, cancels foreground work, and exits `serve` with status `78` within 15 seconds and before further admission.

A transient refresh failure may use the last successful snapshot only until its 45-second expiry. At expiry, control publishes `StaleSince`, denies runner admission, JIT registration, Docker run, backend restart, and dead-man credit, and emits a dedicated cooldown-deduplicated `containment.attestation.stale` alert on the first observation. Each stale foreground observation also advances `ensure_fail_streak` and calls `notify_ensure_failure` as supplemental escalation; alert delivery does not depend on that configurable threshold. A fresh full pass followed by a healthy ensure resets the streak. `serve` exits with status `75` after two denied foreground observations or 75 seconds from `StaleSince`, whichever comes first; the cancellation token makes the wall-clock deadline enforceable even during reconcile/monitor work. Tests use injected clocks, cancellation-aware fake operations, and operation spies rather than flaky CI timing; live release evidence records full-check latency and fast-guard p50/p95/p99 and requires p99 at or below 100 ms.

The host installer must first receive successful static and dynamic install verdicts before image acquisition or live mutation, then install and verify policy, non-unit receipt artifacts, and staged unit candidates while holding the transaction lock. Deferred `install-service` independently obtains and consumes `TransactionAdmission` before its only allowed mutation, installing the two units; ordinary admission must then pass every final receipt path before lock release or start. The shell startup assertion remains defense in depth and consumes only the canonical runtime admission verdict; it does not own a second decision table. Host Docker never invokes VM/Lima recovery, even when a check fails. A failed check returns a typed diagnostic and performs no admission-side Docker, service, config, or live-limit mutation; the sole pre-admission mutation exception is an exact configured Colima/Lima start authorized by a successful static verdict and separate `RecoveryDecision`.

Pre-daemon recovery is not admission. A separate Rust `RecoveryDecision`, derived only from the static-validated proposed endpoint during installation or the persisted normalized endpoint at runtime plus the platform, may start only the exact explicitly configured Colima/Lima backend through the existing bounded command. Canonical host, Docker Desktop, remote, inherited-context, indeterminate, and unsupported-platform endpoints produce `NoRecovery`; a stopped Docker Desktop daemon therefore returns a typed transient dynamic-preflight failure and is never auto-started. After a permitted VM start, full classification and `RuntimeAdmission` are still required before pre-pull or runner reconciliation. Outside a deployment transaction, durable pressure relief remains `systemctl --user stop ezgha.service` followed by ordinary `ezgha stop`; container removal alone is temporary while a supervisor can refill. Transaction-held relief uses the explicit fenced path below.

### Upgrade admission fence

An upgrade must quiesce the currently installed supervisor before image acquisition or any config, helper, receipt, policy, service-manager, Docker-runner, or GitHub-runner mutation. After both read-only install verdicts pass and prior state is snapshotted, the transaction records the old service's active/enabled state, stops only `ezgha.service` when active, and requires `ActiveState=inactive` and old MainPID exit within 30 seconds. Before attempting the runner fence, it acquires `emergency.lock`, atomically publishes a mode-`0600` `Preparing` transaction record with schema/generation/nonce, installer PID/start time, boot ID, canonical intended lock path, config fingerprint, request path, and prior service state, then releases `emergency.lock`. It never waits for `serve.lock` while holding the control lock. It then opens and retains an exclusive `flock` file descriptor within a 15-second timeout for the active config's canonical `state_dir/serve.lock` through the entire mutation or rollback window. After acquisition it reacquires `emergency.lock`, acknowledges any matching request or atomically transitions the same nonce to `Fenced` with the actual lock device/inode, then releases the control lock. A request received in `Preparing` therefore suppresses mutation and restoration/start. Static-verdict JSON supplies the canonical normalized path so shell never reimplements config resolution. The proposed config must preserve `state_dir`, target/scope, and runner name prefix for managed or legacy upgrades; otherwise the transaction fails before stopping anything. Release builds remove the `EZGHA_SKIP_LOCK` escape, retaining lock injection only under `cfg(test)`, so the supported installed `start`, `serve`, and `stop` paths cannot race the transaction.

Stopping the supervisor does not cancel a running job. Managed-upgrade containers already proven beneath `actions.slice` may remain while the fence prevents refill. A legacy migration whose containers are not beneath the target aggregate performs a fixed 30-minute drain while holding the lock: it never cancels a busy job, waits for busy containers to finish, removes only idle managed containers/registrations, and requires zero legacy containers before policy mutation. The installer opens a fixed inheritable descriptor, explicitly clears `FD_CLOEXEC`, acquires the exclusive lock, and passes its number only as `--transaction-lock-fd <n>` to the Rust drain primitive and deferred service installer. Before the first mutation, Rust bounds-checks the descriptor, uses `fstat` to match it to a freshly opened canonical lock file, calls nonblocking exclusive `flock` on the inherited descriptor and requires success, then opens a second description and requires its nonblocking exclusive lock to fail with `EWOULDBLOCK`. The first call is idempotent when the shared open-file description already owns the lock and atomically acquires it if the shell failed to do so; it rejects a third-party owner. Rust never unlocks or closes the inherited descriptor, so the parent retains ownership after the child exits. Wrong inode, closed or exec-lost descriptor, or missing second-description contention is rejected before mutation. A drain timeout restores the formerly active old service and exits before containment/config/helper/image mutation.

During the transaction, `install-service --defer-start --transaction-lock-fd <n> --unit-candidate-dir <path>` is accepted only with that validated inherited lock FD plus fresh `TransactionAdmission`; it validates receipt-bound staged bytes, atomically installs and verifies both units, but cannot start them. On success or rollback, the transaction keeps the lock while restoring bytes and unit state, releases it only immediately before the single final `systemctl --user start`, and verifies that the selected service acquired the same lock before reconciliation. Direct `install-service` remains runtime-admission-gated and uses its ordinary start behavior outside a transaction. An obsolete binary launched concurrently from an unrelated path is outside the supported rolling-upgrade surface; no global process-fencing claim is made.

The `Preparing`/`Fenced` state machine under canonical `emergency.lock` linearizes initial publication, runner-fence ownership, transaction phase transitions, emergency-request publication, abort acknowledgment, and final service handoff. Rust-owned `ezgha emergency-stop --confirm` is the only production command that may coordinate relief without acquiring `serve.lock`. It acquires `emergency.lock`, atomically writes a mode-`0600` request containing the live transaction nonce when present, operator intent, timestamp, and reason, then releases the control lock before waiting for acknowledgment. The wait polls completed/aborting state without retaining any lock, so the transaction can acquire `emergency.lock` to acknowledge. `--cancel-running` is additionally required before it may force-remove any running container. Without that flag, it requests/awaits abort and reports state but performs no running-container deletion.

The emergency command may stop `ezgha.service`, but never starts/restarts a backend or service, registers/refills/creates a runner, changes policy/config/receipts, calls GitHub, deletes registrations, or releases slots. With `--cancel-running`, it removes within a 30-second total deadline only a container whose inspection proves all of: label `ezgha=managed`, valid label `ezgha.runner_id`, exact configured slot/prefix name, and runner ID equal to that slot's persisted assignment. Inspect failure, empty/invalid assignment, label/name mismatch, ambiguous ownership, or sibling-host evidence causes a skip. Partial removal returns a distinct incomplete-relief result with removed, skipped, and failed IDs. Docker inspect and approved `docker rm -f` are the only backend operations allowed; offline GitHub registrations remain for the normal reaper after the transaction is gone.

Before each bounded transaction operation, the installer briefly holds `emergency.lock`, checks for a matching request, and records the next phase. A request is acknowledged only when the installer holds that lock and atomically changes state to `aborting`; no runner-capable operation may begin after acknowledgment. It checks again after each operation and at least once per second during a legacy drain. At final handoff it holds `emergency.lock` continuously across the last request check, `systemctl --user start`, and terminal-state commit. Thus, if the transaction acquires the lock first, a waiting emergency command subsequently stops the newly started service; if emergency acquires it first, the request suppresses start. Abort rolls back all changed bytes and enabled state while retaining `serve.lock`, deliberately leaves the formerly active supervisor inactive, records `aborted`, then releases both locks.

`emergency-stop` waits at most 35 seconds for control-lock acquisition and transaction acknowledgment; timeout returns a distinct incomplete-relief result after its bounded service-stop attempt. If no state record is visible while holding `emergency.lock`, it opens the canonical `serve.lock` separately and probes exclusive ownership with nonblocking `flock`. Success proves no fenced transaction, after which it immediately unlocks/closes the probe and completes/removes a standalone request. `EWOULDBLOCK` without visible state is `OrphanedFence`: it persists the request, stops the service, returns incomplete relief, and never assumes no transaction. Terminal, stale-boot, dead-PID, malformed, or interrupted visible state likewise permits only bounded service stop and optional proven-local removal and never clears or declares the transaction successful.

Ordinary install/start remains fail-closed until tracked `./install.sh --recover-transaction` uses `emergency.lock` plus the nonblocking-fence protocol and never waits on `serve.lock` while holding the control lock. With valid stale/interrupted transaction state and a saved snapshot, it validates no recorded installer is live, restores and verifies the snapshot, records `recovered`, and removes matching state/request records without starting a service. With `OrphanedFence` request but no transaction state/snapshot, its separate orphan branch requires `ezgha.service` inactive and the nonblocking fence probe to succeed; while still holding the acquired probe it atomically records `orphan-cleared`, removes only that validated orphan request, then releases the probe. It performs no rollback, never declares a transaction successful, and does not start a service. A busy fence or active service leaves the request and fail-closed state intact. Normal `ezgha stop` remains serialized by `serve.lock`; ordinary migration drain never invokes emergency cancellation automatically.

On the fixed Linux profile, the deployment receipt records the final config artifact's path, mode `0600`, SHA-256, and parsed `runner.count`; both the receipt and receipt-validated config must equal `10`. Direct `ezgha start` resolves `requested_count = --count.unwrap_or(config.runner.count)` and rejects with policy status `78` unless `requested_count == receipt.runner_count == config.runner.count == 10`. `--count 10` is accepted but is not an override. Rejection occurs immediately after config load and before lock acquisition, backend selection, containment admission, Docker/GitHub/systemctl invocation, ledger access, or any write. After acquiring the lock, ordinary full runtime admission repeats config identity/count validation to close the pre-lock race. Non-Linux legacy profiles preserve existing configured-count behavior. Runtime attestations and permits bind the persisted count, so no internal caller can expand the profile under a valid permit.

### Backend topology

Host Docker at `unix:///var/run/docker.sock` is an allowed production backend. It is not described as VM-contained. Add a backward-compatible defaulted `[backend].docker_endpoint` field to the deny-unknown config schema. New Linux install/admission requires a recognized explicit value and rejects missing, inherited-only, remote, or ambiguous endpoint state; `ezgha init` persists the normalized recognized endpoint it classified. One endpoint-aware `BackendTopology` classifier, owned by `src/backend.rs` and exposed as structured `ezgha topology --json`, combines that persisted endpoint with Docker daemon metadata: the canonical host socket plus a same-kernel Linux daemon is `HostDocker`; a recognized explicit Colima, Lima, or Docker Desktop socket plus VM daemon metadata is `VmDocker`; contradictory metadata, remote endpoints, and unknown sockets are `Indeterminate`. `Platform.daemon_in_vm` is only one metadata input and is never the classifier by itself. Shell gates consume the structured Rust result and do not duplicate the endpoint decision table. A Linux install/start gate rejects `Indeterminate`, while existing Mac and pre-existing runtime paths preserve their non-fatal warning/no-op behavior.

Legacy Mac configs without `[backend].docker_endpoint` use a Darwin-only compatibility resolver until their next `ezgha init` or `install-service`. It considers, in order, a nonempty explicit override, the installed launchd plist endpoint, the active Docker context, and recognized Colima/Lima/Docker Desktop sockets; it accepts only one normalized consistent endpoint and returns `Indeterminate` on disagreement, unknown transport, or no evidence. The resolved endpoint is persisted atomically during `init`/`install-service`; after persistence the config value overrides ambient state. A uniquely proven Colima/Lima endpoint retains the existing bounded recovery, while Docker Desktop, ambiguity, or missing evidence produces `NoRecovery` and never invokes Colima/Lima. This compatibility resolver is forbidden on Linux.

The generated unit always emits the config endpoint, including `unix:///var/run/docker.sock`, and clears inherited `DOCKER_CONTEXT`; every Rust Docker subprocess uses that same value and removes `DOCKER_CONTEXT`. The generated Linux service has no unconditional `lima-vm@colima.service` dependency, and backend recovery must never start Lima for `HostDocker`; a failed HostDocker permit is a hard no-op, never a VM recovery request. Only explicit Colima/Lima endpoints may use the existing bounded recovery path; Docker Desktop is classifiable when reachable but is non-recoverable by this implementation when stopped. An inactive legacy Lima unit may be disabled after the backend endpoint is proven; no VM disk is deleted.

For the `HostDocker` branch, the service may start only after the containment preflight establishes all of the following; `VmDocker` reports this host profile as not applicable and proceeds only through its separate VM gate:

1. The configured endpoint is exactly the canonical host socket, not a Colima/Lima or remote endpoint.
2. Docker reports cgroup v2 with the `systemd` cgroup driver.
3. The configured cgroup parent is `actions.slice`.
4. `/sys/fs/cgroup/actions.slice` exists under the system manager.
5. Its memory, swap, CPU, and task limits exactly match the declared fixed profile.
6. `actions.slice` is enrolled for memory-pressure handling.
7. The deploy owner's `user@UID.service` is not actively monitored for memory pressure or swap, no ancestor is enrolled with `kill` for either policy, and the broad service reports `ManagedOOMPreference=none` plus `OOMScoreAdjust=0` rather than a subtree-wide exemption.
8. The tracked finite `agents.slice` is effective and no unlimited local override is active.
9. Neither the installed `ezgha.service.d/10-oomd-omit.conf` nor its effective `ManagedOOMPreference=omit`/`OOMScoreAdjust=-1000` remains.
10. Unprivileged bounded `oomctl` queries work and list the intended workload roots, including effective user-manager `agents.slice` and `automation.slice` enrollment.
11. The host has at least 62 GiB RAM and 32 logical CPUs; this fixed hardware profile is rejected on a smaller machine instead of silently consuming its reserve.

Any failed invariant blocks new runner admission and emits a diagnostic naming the mismatched property. It does not restart Docker, Colima, the desktop, or the physical host.

## Components and Ownership

### Repository policy

`CLAUDE.md` owns the full crash-containment tenet. `AGENTS.md` contains a concise pointer because both files exist independently. `README.md` describes the user-visible topology accurately and stops claiming that Jeff-Ubuntu runners are inside Colima when host Docker is active. `/up` writes a short receipt under `roadmap/`.

### System policy artifacts

`systemd/host/actions.slice` owns the host runner aggregate. A separate top-level `systemd/host/ezghaproof.slice` contains `ezghaproof-hardlimit.slice` and `ezghaproof-oomd.slice`, so a synthetic proof is never a descendant of the monitored production runner root. Fixed root-owned `ezgha-hard-limit-proof.service` and `ezgha-oomd-proof.service` units are the only proof launchers; they use a repository-owned Python-stdlib allocator, have no Docker socket or credentials, and cannot accept an arbitrary command. Hard-limit mode deliberately exceeds its child `MemoryMax`. Oomd mode allocates and continuously touches an anonymous working set above its child `MemoryHigh` but below `MemoryMax` for 75 seconds. Because systemd exposes pressure duration only as the global `DefaultMemoryPressureDurationSec`, the harness reads and records the effective merged oomd configuration, rejects a missing/unparseable duration or one above 45 seconds, and requires the child's exact `memory.pressure` `full avg10` value to stay at least 20% continuously for that duration before accepting a correctly named journal victim. Allocator exit without both the continuous measured interval and victim never passes. The proof harness uses privileged `systemctl` only with those literal unit names and never permits `systemd-run` or a shell. `systemd/host/-.slice.d/90-ezgha-oomd-boundary.conf` and `systemd/host/user@.service.d/90-ezgha-oomd-boundary.conf` own the broad vendor-policy overrides. Existing `systemd/agents.slice` and `systemd/automation.slice` own user workload limits.

The workload-only oomd policy is intentional: Ubuntu's vendor `user@UID.service` kill behavior is the broad crash blast radius being removed, not a useful workload safeguard. All desktop ancestors are explicitly `auto`, and the user service is neutral rather than `avoid`/`omit` or negatively scored; `oomctl` must show only the finite workload roots (and an active proof root) as kill-capable roots. The proof must demonstrate that a workload victim does not terminate the user manager, Warp, or unrelated desktop processes.

### Installation

`scripts/host/install-crash-containment.sh` installs and verifies system-scope artifacts with explicit privilege escalation. It supports a read-only capability/current-use `--preflight`, a read-only installed-state `--check`, and an applying `--install` mode. `install.sh` invokes the installer on systemd Linux hosts and fails rather than claiming success when the configured host-Docker fleet lacks the required system controls.

After an allowed local candidate build, installation has two read-only phases. Static preflight first validates a mode-`0600` proposed config with an explicit endpoint, hardware, privilege, deployment state, and rollback storage without requiring a reachable VM daemon. The state classifier does not treat a config file alone as an upgrade:

- `Bootstrap` requires no receipt/helper set, generated user units, active/enabled runner service, managed-prefix container, or registered-prefix runner. The active config may be absent or byte-identical to the proposed config and is staged data, not deployment evidence; any partial runtime/policy artifact is `Mixed`.
- `ManagedUpgrade` requires a complete receipt, every receipt-listed artifact, both generated user units, the active config, and all expected effective cgroups. It enforces the current-use margins.
- `LegacyMigration` requires a recognized complete pre-receipt service/config/runtime signature. It is never adopted as fresh and must pass the upgrade admission fence plus bounded legacy-container drain.
- `Mixed` covers partial receipts/helpers/units/cgroups, an unrecognized differing active config, orphaned registered-prefix runners, or any other incomplete combination and fails before image, runner, policy, config, or service mutation.

A receipt whose unit entries exist only in the receipt-bound candidate directory is an allowed transitional state solely inside the running transaction while the validated exclusive lock is held. It is never a persisted deployment classification. After process interruption or without that exact lock/candidate proof it classifies `Mixed`, ordinary admission fails, and no service may start; rollback removes or restores the receipt and all listed artifacts.

This supports the documented two-pass bootstrap: the first `./install.sh` performs only `cargo build --locked --release` in the checkout and requests `target/release/ezgha init`; `init` may read endpoint/daemon metadata but cannot start/recover a backend or build/pull/run an image, and writes only an explicit-endpoint starter config. The second `./install.sh` treats that config-only state as staged `Bootstrap`. It does not replace the installed binary before preflight. Current `install.sh` config-presence auto-start/restart is removed; only the containment transaction may atomically promote the candidate binary and call `install-service`. Only a recognized explicit Colima/Lima endpoint may authorize starting that exact configured VM between static and dynamic phases. Dynamic preflight then proves daemon topology, Docker cgroup v2 with the `systemd` driver, and unprivileged `oomctl`. Both phases precede admission quiescence, image acquisition/build/pull, and every installed/live mutation. Canonical host, Docker Desktop, remote, inherited-only, indeterminate, and unsupported-platform endpoints never recover a VM; a failed phase exits without image work or changing the installed binary, generated service, config, helpers, or live limits. The supported portable target is a fresh systemd Ubuntu host meeting the declared 62-GiB/32-CPU profile; scaled profiles are a separate reviewed design, not an implicit fallback.

Installation removes the known `agents.slice.d/99-local-unlimited.conf` drift file and the live `~/.config/systemd/user/ezgha.service.d/10-oomd-omit.conf`, disables and removes the obsolete `psi-oom-watcher` service/timer plus its installed stable script, and reloads the appropriate managers without restarting the desktop or physical host. It verifies the exemption's unit configuration is gone before restart, then verifies the new MainPID's `/proc/<pid>/oom_score_adj` and effective properties after restart. Before lowering an active hard limit, it records `memory.current` and `memory.stat` for the actual system and user cgroups, but uses the enforceable `memory.current` value without discounting file cache to prove use fits below the proposed `MemoryHigh` with a workload-specific activation margin: 1 GiB for actions, 1 GiB for agents, and 512 MiB for automation; otherwise it leaves the live policy unchanged and fails. The actions margin permits the declared ten-container maximum of about 24.4 GiB below `MemoryHigh=26G`. The single `install.sh` transaction snapshots the installed `ezgha` binary bytes/path/mode/digest, live config, all replaced system/user policy and helper files, both generated `ezgha.service` and companion `ezgha-alert@.service`, the versioned deployment receipt and every receipt-listed artifact, the legacy watcher service unit, timer unit, and installed stable script, the live exemption, and the applicable prior active/enabled state for every affected unit. After both read-only verdicts it performs the upgrade admission fence, then atomically installs the candidate binary, mode-`0600` proposed config, and helper/policy set. Any quiescence, binary, config, containment, assertion, service regeneration, restart, or post-start verification failure restores every file byte-for-byte, reloads both managers, restores enabled/disabled and active/inactive state (enabling or starting only units that were previously enabled or active), and verifies the effective restored state before returning failure. It installs only persistent tracked units and never creates overriding `systemctl set-property` drop-ins. It never deletes VM data.
The installer also publishes a versioned deployment receipt atomically with final `config.toml`, the candidate binary, helper set, and staged generated-unit candidates. The receipt records the deployed source commit SHA and, for config, the binary, every helper, `ezgha.service`, and `ezgha-alert@.service`, the artifact role, candidate/source path, final installed path, exact mode, and SHA-256. The config entry additionally records parsed `runner.count`; fixed Linux requires mode `0600` and count `10`. Config, files, and unit candidates are staged, mode/digest/count-checked, flushed, and renamed before the receipt is renamed into place; a receipt that does not describe this complete deployment set is invalid. The transaction-scoped permit validates final config and installed binary/helpers plus staged unit candidates, allowing deferred service installation without circularly requiring new units to be installed first. After deferred installation, ordinary admission validates every final receipt path, mode, digest, and parsed count before lock release. Runtime commands execute the receipt-validated config and installed immutable binary/helpers and never use a mutable checkout as deployment evidence. The receipt and every artifact it describes are one rollback unit: bootstrap rollback removes them together, upgrade rollback restores their prior bytes together, and either path rejects partial state.

### Startup preflight

`scripts/host/assert-crash-containment.sh` is a read-only executable installed under `~/.local/libexec/ezgha/`. The generated `ezgha.service` uses a tracked startup wrapper as its main `ExecStart`, passing the exact binary path returned by `current_exe()` and the exact config path: it runs the canonical `ezgha containment-check --admission --json` gate (with the shell assertion as defense in depth), exits `78` for a proven policy violation, returns the assertion's transient exit `75`, and `exec`s the real `ezgha serve` process after success. The assertion itself performs three Docker queries over at most 15 seconds; with `RestartSec=30`, five failed starts fit inside the preserved `StartLimitIntervalSec=300`/`StartLimitBurst=5` window and then stop. `RestartPreventExitStatus=78` applies to the main process, and `TimeoutStartSec=150` bounds the 15-second assertion plus the daemon's existing 120-second readiness window. Backend classification uses the configured Docker endpoint plus daemon metadata, not kernel-version comparison alone. Host Docker requires the host profile above; VM Docker reports this host preflight as not applicable and leaves VM-specific verification to a mutually exclusive VM gate. All final deployment-receipt paths, modes, and digests must match the receipt, not a mutable checkout.

Service regeneration preserves failure alerting. The main unit retains `OnFailure=ezgha-alert@%N.service` plus a fail-open `ExecStopPost` that invokes the exact installed binary/config with `systemd-alert-hook --source exec-stop-post`. The companion `ezgha-alert@.service` remains a 30-second `Type=oneshot` invoking the same binary/config with `--source on-failure`; both units inherit the persisted endpoint and cleared Docker context, and both are included in transactional rollback tests.

The assertion returns distinct statuses for a proven policy violation and a transient inability to query Docker. The generated service permits recovery from a short transient failure within its existing bounded start window, while a proven policy violation remains fail-closed and clearly logged. This is normal service recovery, not a second repair daemon and never mutates containment policy.

### Verification

`docs/verify-exit-criteria.sh` verifies effective values rather than file presence. Host-Docker and Colima gates are mutually exclusive: the host path checks the system `actions.slice`, the `systemd` Docker cgroup driver, actual cgroup ancestry for every managed container, user workload caps, the `user@` OOM policy and all desktop ancestors, effective `oomctl` roots, and the absence of unlimited/runtime overrides and `ezgha.service` OOM exemptions. It also validates the versioned deployment receipt against installed binary, helper, and generated-unit paths, modes, and digests. It does not include an inactive Lima slice in host-Docker budget arithmetic or require a live guest. `doctor-runner` reports the same topology without mutating it.

## Data Flow

1. `install.sh` may build the exact local candidate binary locally (the build cannot invoke Docker), classifies `Bootstrap`, `ManagedUpgrade`, `LegacyMigration`, or `Mixed`, then requires a successful static install verdict. For an explicit recognized Colima/Lima endpoint on a supported platform only, it may start that exact VM, then requires the dynamic Docker-backed install verdict. Host Docker and Docker Desktop never recover a VM. Neither verdict is an admission capability.
2. After both verdicts and a read-only transaction snapshot, an upgrade stops the old supervisor, verifies it inactive, and holds canonical `serve.lock`; legacy containers drain without cancelling busy jobs. Both phases and admission quiescence must pass before image acquisition or any other config/helper/policy/runner mutation.
3. The host containment installer copies tracked units and the root-owned proof allocator to their system and user destinations, atomically retires the old watcher and both source/live exemption state, reloads managers, and checks effective properties including `oomctl` roots.
4. After containment, installed binary/helpers, staged generated-unit candidates, and their deployment receipt are effective, transactional `ezgha install-service --defer-start --transaction-lock-fd <n> --unit-candidate-dir <path>` validates the lock and staged receipt, then obtains fresh `TransactionAdmission` before atomically installing both units without starting them. A subsequent ordinary `ezgha containment-check --admission --json` must validate every final receipt path before the transaction releases the old lock for one service start. Direct `serve` obtains full `RuntimeAdmission` before pre-pull, starts its bounded background `AttestationSupervisor`, and each `ensure_count` tick mints a cheap fresh `TickAdmission` from an unexpired successful snapshot before runner creation. Transaction failure restores prior artifacts; an emergency request aborts and rolls back while deliberately leaving the old supervisor inactive.
5. The endpoint-aware topology enum controls budgeting: `HostDocker` ignores VM-only guest-reserve fields and delegates the aggregate ceiling to system `actions.slice`; `VmDocker` retains the existing guest reserve and VM envelope; `Indeterminate` is rejected by new Linux install/start gates while preserving the bounded legacy-Mac resolver.
6. `ezgha` creates each runner with `--cgroup-parent=actions.slice` plus per-container memory, CPU, PID, swap, and security limits.
7. The system manager accounts every runner beneath the finite aggregate.
8. Under ordinary pressure, `MemoryHigh` throttles and reclaims workload memory.
9. Under sustained pressure, `systemd-oomd` may kill an eligible descendant of that monitored workload root; at the hard boundary, the kernel enforces `MemoryMax` within the limited cgroup.
10. Separate hard-limit, oomd-selection, ten-worker execution, and live desktop-survival proofs record what actually happened instead of inferring behavior from configuration.

## Residual Risks

- The approximately 8.5-GiB remainder (`62.48 - 54 = 8.48 GiB`) is not reserved memory. Docker, the kernel, desktop applications, and other system services remain outside the three hard caps and can still trigger global kernel OOM.
- Independent oomd monitoring roots do not provide a global runner-before-agent order. Each root selects only among its own eligible descendants.
- `MemorySwapMax=0` avoids runner swap thrash but reduces the time available for PSI-based oomd action during an abrupt allocation burst; `MemoryMax` is the final boundary.
- `CPUQuota=2000%` equals the ten configured 2-CPU container maxima and reserves 12 of 32 logical CPUs for the host; the capacity proof still checks real ten-job execution.
- Portable block-device bandwidth caps require a measured device baseline. `IOWeight=25` gives runner I/O lower relative priority where the controller is available; the verifier reports unavailable controllers rather than asserting protection.

## Failure Handling

| Failure | Required behavior |
|---|---|
| Host `actions.slice` missing or infinite | The main startup wrapper exits `78`; no new runners start and systemd does not restart the policy violation. |
| Static or dynamic install preflight fails, or scoped admission is missing/expired/receipt-invalid | A preflight failure leaves image/Docker-runner/live policy state unchanged; only a successful static verdict for an explicit recoverable Colima/Lima endpoint may authorize the exact VM start needed for dynamic preflight. Docker Desktop remains stopped and returns a typed transient failure. Failed `RuntimeAdmission` blocks direct start, serve pre-pull, and direct `install-service`; missing, revoked, or stale `TickAdmission` blocks runner creation without backend restart or dead-man credit; failed `TransactionAdmission` blocks deferred unit installation/reload. Ordinary stop/removal stays available outside a transaction, the explicit emergency path remains available while the lock is held, and Host Docker never asks VM/Lima recovery to repair a failed check. |
| Linux direct count differs from receipt-backed config or fixed value 10 | Exit `78` immediately after config load with zero lock, backend, containment, Docker, GitHub, ledger, or write operation. Full post-lock admission repeats the validation before reconciliation. |
| Background attestation proves policy drift | Revoke all permits, emit one critical typed alert, cancel foreground work through `AdmissionControl`, perform no further runner admission, and exit `serve` with `78` within 15 seconds. |
| Background attestation is transiently unavailable past the 45-second snapshot TTL | Deny admission, emit dedicated `containment.attestation.stale` on first observation, advance the ensure failure streak as supplemental escalation, skip backend restart/dead-man credit, cooperatively cancel foreground work, and exit `75` after two denied observations or 75 seconds from `StaleSince`. |
| Confirmed emergency stop during a deployment transaction | Publish a nonce-bound request under `emergency.lock`; abort acknowledgment is the no-further-runner-operation linearization point. The installer rolls back under the fence and leaves the old supervisor inactive. Holding the control lock across final start ensures an earlier request suppresses start and a later request stops the newly started service. Running containers are removed only with `--cancel-running` and exact label/name/runner-ID/slot proof; partial relief is reported distinctly. |
| Bootstrap/upgrade state is mixed, or upgrade quiescence fails | Installation fails before image or containment/config/helper mutation. If the old service was stopped, it is restored only when formerly active; busy jobs are never cancelled. |
| Docker query is temporarily unavailable | The assertion retries for at most 15 seconds and returns `75`; normal service restart retries at 30-second intervals and the existing five-start/300-second limiter stops a persistent outage. After fixing the prerequisite, the tracked runbook requires a passing `ezgha containment-check --admission --json`, then `systemctl --user reset-failed ezgha.service` and `systemctl --user start ezgha.service`; no monitor resets or loops the limiter. |
| One runner exceeds its limit | The cgroup-local OOM is contained to that runner scope. Whole-container exit is claimed only when effective `memory.oom.group` or observed exit behavior proves it. |
| Runner aggregate exceeds `MemoryHigh` | Reclaim/throttle occurs inside `actions.slice`. |
| Sustained runner pressure | An eligible runner descendant is selected within `actions.slice`; no cross-root runner-before-agent order is claimed. |
| Agent aggregate exceeds its envelope | Pressure handling remains within `agents.slice`; desktop survival is a live integration result, not a static guarantee. |
| `systemd-oomd` inactive | Hard cgroup limits still contain workloads; verifier reports degraded defense in depth. |
| Host Docker selected while Lima unit is enabled | Verification fails with topology drift; installation may disable an already inactive Lima unit but never stops a live VM automatically. |
| System privilege, topology, driver, hardware, or `oomctl` preflight unavailable | Installation fails before mutation with the exact unmet prerequisite; it does not deploy a falsely green user-only approximation or restart the fleet. |
| Post-mutation verification or gated restart fails | Restore final config, system/user policy, binary/helper files, the deployment receipt, both previous generated user units, retired watcher/exemption files, and every prior active/enabled state; verify the rollback before returning failure. |
| Pressure proof harms the desktop or host | Test fails immediately and blocks deployment; no threshold is accepted from synthetic unit tests alone. |

## Implementation Preconditions

- The deploy owner must have non-interactive or interactive `sudo` authority to install system units under `/etc/systemd/system`; user-only installation cannot enforce Docker's system cgroup hierarchy.
- The live deployment must follow the repository's single-writer checks before restarting `ezgha.service` or running the live harness.
- The bounded pressure proof requires privilege to start the two fixed tracked proof services by literal name; arbitrary transient units and commands are prohibited. The repository supplies the fixed bounded allocator rather than depending on `stress-ng` behavior.
- Live activation requires current usage to fit below each proposed `MemoryHigh` with the declared workload-specific margin: 1 GiB for actions, 1 GiB for agents, and 512 MiB for automation; otherwise deployment stops before installing or reloading units.
