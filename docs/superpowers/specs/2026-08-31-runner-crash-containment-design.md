# Runner Crash Containment Design

**Date:** 2026-08-31
**Status:** Revised after formal `/advice` review; implementation not started
**Primary goal:** Keep the physical Ubuntu host, desktop session, Warp, and operator tools responsive while ten Linux GitHub Actions runners execute concurrently.

## Problem Statement

The production fleet currently runs ten runner containers through the host Docker daemon. Each container has a finite memory, CPU, and PID limit, but the shared host `actions.slice` has infinite aggregate limits. The tracked finite `actions.slice` is installed only inside Colima, so it does not constrain host-Docker containers. At the same time, a local `agents.slice` drop-in overrides the tracked finite values with infinity, while Ubuntu's vendor `user@.service` policy monitors the entire user manager for memory pressure.

That topology inverts the intended failure order. During runner refill bursts, `systemd-oomd` can kill the deploy owner's `user@UID.service`, taking Warp, tmux, Codex, and the desktop session together, while the runner aggregate remains unbounded. Colima is not the root requirement: the availability requirement is that lower-priority workloads fail before the operator session and physical host.

## Goals

1. Keep exactly ten Linux runner slots configured and available; reducing runner count is not an accepted containment mechanism.
2. Make runner memory, CPU, swap, and process use finite in one host-level aggregate in addition to existing per-container limits.
3. Make interactive agent and automation aggregates finite so they cannot consume the host reserve.
4. Enforce runner, agent, and automation pressure with finite cgroup limits while no production or desktop root is a `systemd-oomd` kill target.
5. Refuse new runner admission when required containment is missing or infinite.
6. Keep every production control, installer, verifier, and policy statement git-tracked and portable to a fresh Ubuntu machine.
7. Preserve operator-only authority over physical-host reboot, shutdown, VM teardown, and other broad lifecycle actions.

## Non-Goals

- Containing deliberately malicious workflow code or kernel exploits. Host Docker shares the host kernel and is accepted for this trusted-workload threat model.
- Making Colima a required Linux backend.
- Adding another watchdog, polling daemon, or automatic host/VM restart loop.
- Reducing the ten-runner Linux capacity contract.
- Reworking runner registration, GitHub API reconciliation, or per-job lifecycle behavior.

## Approaches Considered

### 1. Host Docker with a fail-closed host resource envelope (recommended)

Keep the existing host Docker execution path. Add a real system-level `actions.slice`, enforce finite aggregate limits, disable production and broad desktop `systemd-oomd` enrollment, and require a startup preflight before runner admission.

This has the fewest runtime layers, avoids QEMU overhead, and directly fixes the observed failure: unbounded workload aggregates combined with a desktop-wide OOM target. It does not provide a separate kernel security boundary, which is outside this design's threat model.

### 2. Colima-only Linux runners

Repair `/dev/kvm` boot ordering, converge the legacy and canonical Colima profiles, remove writable host-home mounts, size QEMU, and run Docker inside the VM. This provides a stronger security boundary, but QEMU remains a large host process requiring the same cgroup/OOM policy. It also introduces VM boot, disk, socket, and lifecycle failure modes that do not advance the primary crash-containment goal.

### 3. Colima primary with host-Docker fallback

Prefer Colima but silently switch to host Docker when the VM is unavailable. This is rejected. The August 27 host-Docker drop-in was created immediately after repeated Colima failures and bypassed the only tracked aggregate limit. A topology-changing fallback makes the active safety contract unknowable during an incident.

## Architecture

### Resource hierarchy

The host uses three workload aggregates with non-overlapping ownership:

```text
-.slice
├── actions.slice                 system scope, Docker container scopes
│   └── docker-*.scope            one ephemeral runner per scope
├── ezghaproof.slice              system scope, synthetic proofs only
│   ├── ezghaproof-hardlimit.slice
│   └── ezghaproof-oomd.slice
├── user.slice
│   └── user-1000.slice
│       └── user@UID.service
│           ├── agents.slice      interactive coding agents and descendants
│           ├── automation.slice  AO and factory daemons
│           ├── app.slice         Warp and desktop applications
│           └── session.slice     GNOME session services
└── system.slice                  Docker daemon and host services
```

`actions.slice` is a root-owned system slice because Docker creates container scopes through the system manager. Installing a user-scoped unit with the same name does not constrain those scopes and is forbidden as evidence of containment.

### OOM ownership

- `actions.slice`, `agents.slice`, and `automation.slice` set both `ManagedOOMMemoryPressure=auto` and `ManagedOOMSwap=auto`; no production pressure limit is installed or treated as effective. `MemoryHigh`, `MemoryMax`, `MemorySwapMax`, CPU, and task limits are the production enforcement mechanism.
- Six tracked drop-ins force both managed-OOM policies to `auto` on `-.slice`, `user.slice`, the portable `user-.slice` prefix inherited by the deploy owner's `user-UID.slice`, `user@UID.service`, `app.slice`, and `session.slice`. The broad `user@UID.service` also resets `ManagedOOMPreference=none` and `OOMScoreAdjust=0`; setting it to `omit` or assigning a negative score is forbidden because that protects the entire session subtree and can displace kernel/oomd victims rather than containing the source. `ManagedOOMMemoryPressureLimit=0%` is not treated as protection because systemd ignores that property unless pressure mode is `kill`. This removes the vendor `user@UID.service` and root-wide swap kill targets that formed the previous crash blast radius: Warp, tmux, Codex, and the desktop manager must not be selected as one unit. During ordinary admission, `oomctl` must contain no production or broad desktop kill root. Only the opt-in `ezghaproof-oomd.slice` may appear, and only while its separately labeled proof is active.
- Hard `MemoryMax` limits remain the deterministic last boundary even if `systemd-oomd` is unavailable or slow.
- No workload receives `OOMScoreAdjust=-1000`. Protected workload exemptions invert the intended kill order and are removed from the host-Docker topology.
- Supported agent launchers have no environment escape hatch around `agents.slice`; every detected supported agent CLI process must be a descendant of the finite aggregate before deployment proceeds. Existing unscoped processes are reported and allowed to exit or be relaunched, never killed automatically.
- Production has no oomd victim-selection promise. `MemoryHigh` applies reclaim pressure and `MemoryMax` invokes a cgroup-local kernel OOM when the hierarchical hard limit is reached.
- `MemorySwapMax=0` prevents runner swap thrash. Agent and automation swap caps remain finite, but no production root is selected automatically in response to system-wide swap use.
- Disabling root-wide and production swap monitoring is an explicit blast-radius tradeoff. The last whole-session incident reached about 15.6 GiB swap; deployment records current `SwapTotal`/`SwapFree` plus each workload root's `memory.swap.current` and `memory.swap.peak`, and the release evidence carries those values beside the 54-GiB cap sum and at least 8-GiB arithmetic RAM reserve. The uncapped desktop, kernel, Docker daemon, and other system memory remain residual global-OOM risk; the reserve and finite workload caps are containment evidence, not a claim that those consumers cannot exhaust RAM or swap.

### Admission permit

Rust owns a short-lived opaque `AdmissionPermit` through one canonical containment implementation. `ezgha containment-check --install-static --json` exposes a read-only verdict for the mode-`0600` proposed endpoint, hardware, deployment state, privilege, current use where applicable, and rollback storage without requiring a reachable VM daemon. For an explicitly configured recoverable Colima/Lima endpoint only, that verdict may authorize the separate exact-backend recovery decision. `ezgha containment-check --install-dynamic --json` then exposes a read-only verdict for reachable endpoint topology, Docker's cgroup driver, and `oomctl`; both install verdicts must pass before image work but neither returns an admission capability. `--admission` exposes the stricter runtime verdict after effective installed cgroup/oomd policy and every final deployment-receipt artifact pass. Internal Rust callers use that same implementation to obtain an in-memory permit with a private scope and expiry. `RuntimeAdmission` authorizes only the established runtime mutation paths after final installed-state validation. Private `TransactionAdmission` is callable only by deferred service installation with a validated inherited transaction-lock FD and candidate directory; it validates every non-unit receipt artifact at its final path and both unit candidates at their receipt-bound staged paths, and authorizes only atomic installation, verification, and manager reload for those two units. It cannot reach service start, pre-pull, reconciliation, registration, or runner creation. The CLI JSON never serializes or accepts either permit, so an environment variable, CLI argument, or shell-generated JSON cannot forge one.

Every Linux runner-resource or external control-plane side effect is typed at its call site as either `AdmissionMutation` or `ReliefCleanup`; untyped Docker, GitHub, runner-ledger, quarantine, workspace, or runner-control writes are forbidden. A third type, non-capability `AuditStateWrite`, owns only bounded local audit/history, alert, and failure-counter persistence. Its API cannot reach Docker, GitHub, runner ledgers, quarantine/resource mutation, retry, dispatch, dead-man credit, or permit issuance. A separate private non-capability `ReadOnlyCapacityObserver` can perform only exact managed-container inventory, `docker top`, captured marker reads, and `/proc/<pid>/cgroup`; it cannot write state or obtain an effect gate. `containment-calibrate` composes that observer with an independent `AuditStateWrite` sink, and neither API can construct, hold, or call the other's interface. Direct `start`, direct `serve` before pre-pull, direct `install-service`, and direct `canary-once` perform the full bounded check synchronously. Long-lived `serve` performs one full check before pre-pull, then owns an `AttestationSupervisor` with exactly one read-only full check in flight. It checks Docker, `systemctl`, `oomctl`, config, receipt, SHA-256 digests, endpoint/topology, fixed count, cgroup state, and policy, then atomically publishes a non-capability `RuntimeAttestation` containing pass/failure class, observation generation, revocation epoch, completion instant, boot ID, normalized endpoint, persisted count, and receipt/config metadata identities. The reconciliation thread never invokes or joins those probes and never charges them to its 30-second cadence or the shared 75-second queue-monitor budget.

The following monotonic-clock bounds are normative and receive fake-clock boundary tests plus release-acceptance calibration evidence collected while the exact deployed enforcement remains active:

| Control | Bound | Required result and activation evidence |

The supervisor persists a bounded `AuditStateWrite` ring of at least 128 completed production attestation observations. Each record contains sequence, monotonic start/completion, prior-completion-to-start lag, duration, outcome/failure class, boot ID, observation generation, and receipt/config identities; it contains no permit or mutation capability. `ezgha containment-calibrate --observe-only --samples 100 --capacity-run <captured-run-evidence.json> --output <path>` consumes 100 consecutive records from that production scheduler. At each consumed completion sequence its `ReadOnlyCapacityObserver` performs only the narrow observation above; the result is keyed to that attestation sequence and must prove the same ten captured workflow workers beneath `/actions.slice`. The collector never launches a second attestation loop, mints/publishes a permit or `RuntimeAttestation`, changes the revocation epoch, alerts/cancels/restarts, takes an effect gate, or invokes any Docker lifecycle, GitHub, or manager mutation. Its separate `AuditStateWrite` sink performs the only write: one atomic evidence artifact.

`attestation-calibration.json` schema 1 binds mode, exact boot ID, receipt/config digests, captured run ID/attempt/workflow SHA, thresholds, all raw samples, the current receipt-bound assertion/provenance and pre-pull/READY timing records, and summary verdict. Every sample independently binds exact ten-worker IDs/markers/cgroups at its completion. A restart, boot/artifact identity change, failed/timed-out record, sequence gap, lag over 20 seconds, missing capacity observation, fewer than 100 consecutive records, rank-99 duration over 5000 ms (`ceil(0.99*n)`), fast-guard rank-99 over 100 ms, assertion/provenance over 10 seconds, or pre-pull/READY over 60 seconds fails release acceptance. Calibration failure never cancels the captured run or a running job; the deployment remains fail-closed for new mutation according to its ordinary attestation state and is rolled back through the tracked transaction if release acceptance cannot pass.

`AdmissionMutation` covers every automatic service-loop slot reserve, runner-ID record or release, quarantine write, workspace reset, Docker pull/run/rm, GitHub JIT POST, runner DELETE, workflow cancel/force-cancel, canary dispatch, and stale/zombie reconciliation side effect. `ensure_count`, the in-process reaper, and the canary scheduler receive an `AdmissionIssuer`; immediately before each atomic local commit or actual child-process spawn, the owning call site invokes subprocess-free `mint_mutation()`. A one-use `TickAdmission` never authorizes a batch, callback, retry loop, sleep, or second child. Retrying GitHub helpers receive a private issuer callback and mint independently before every POST or DELETE attempt, including every backoff retry and each JIT conflict-delete-retry command. Read-only list, inspect, probe, and poll operations need no permit. The standalone `cleanup-stuck-runs.sh` and `queue-backlog-drain.sh` become permanently read-only: their apply/cancel flags and every GitHub POST/DELETE helper are removed and rejected before any `gh` invocation. Both doctor entrypoints delegate `--prove` only to receipt/config-bound Rust `canary-once`, which performs admission and returns correlated JSON; the shells never dispatch directly. Automatic queue cleanup runs only inside the lock-owning supervisor through the same issuer; no scheduled shell or second process retains GitHub mutation authority.

A tracked declarative executable-effect inventory closes the source boundary. Every active service, timer, path, socket, plist, executable shell/Python file, workflow, doctor, installer, and command/skill surface has exactly one closed class: `RustGated`, `BootstrapPrivileged`, `ImmutableImagePublisher`, `ProofEffect`, `ReadOnly`, `CredentialRefresh`, `LocalRetentionCleanup`, `AlertDelivery`, `MacAuxiliaryManager`, `ManualAgentSessionMigration`, or `Retired`. Scheduled `ExecStart` and plist `ProgramArguments` targets must resolve to exactly one record, and every non-Rust class names its exact allowed targets and prohibited runner/Docker/GitHub-manager/host effects. `BootstrapPrivileged` applies only to the tracked pre-quiescence administrator bootstrap: exact helper, root-owned authorization metadata, same-directory temporary files, and one sudoers drop-in, with root-owned safe parent chains and byte-exact rollback; it has no Docker, GitHub, cgroup, manager, runner, lock, or application-state authority. `ImmutableImagePublisher` applies only to `.github/workflows/runner-image.yml` on GitHub-hosted `ubuntu-latest`, triggered by the exact workflow/Dockerfile/context paths. It may read the checkout, build and push only `ghcr.io/jleechanorg/ezgha-runner:<source-sha>`, resolve its immutable repo digest, attest the source/workflow/Dockerfile/context identities, and upload that machine-readable provenance artifact. It has no self-hosted label, production Docker socket, repo-content write, workflow dispatch, issue/runner-manager, service/VM/host-lifecycle, or arbitrary package target authority. `ProofEffect` permits only the two literal synthetic proof-unit lifecycles and one selector-validated capacity workflow dispatch after `EZGHA_RUN_PRESSURE_PROOF=1`, a non-CI guard, and successful read-only containment. Token refresh, mission-output retention, and alert delivery remain narrow named local classes. Mac plist installation, Colima trim, and dashboard publishing are disconnected `MacAuxiliaryManager` effects with no Linux install/doctor/CI/supervisor edge. The obsolete 1-GiB 9p/`limactl` probe is retired. Unclassified GitHub writes, Docker lifecycle verbs, mutating manager/VM commands, `systemd-run`, cgroup-control writes, privileged shell, and retired command suggestions fail CI; the publisher's exact hosted build/push is the sole inventory-declared Docker/GHCR exception.

Minting reads the latest successful snapshot, rechecks boot ID plus receipt/config metadata identity, and returns a one-use permit bound to the current revocation epoch with expiry at the earlier of five seconds after issue or snapshot expiry. One private `EffectCoordinator` is the sole linearization authority for runner/control-plane mutation, deployed-file or manager mutation, and backend-start recovery. Its noninterchangeable gates are `AdmissionGate` for one `AdmissionMutation`; `DeploymentGate` for one receipt-enumerated operation under the exact nonce-matched `Fenced` transaction, with `TransactionAdmission` additionally required for deferred unit commits, or under direct-install `RuntimeAdmission`; `RecoveryGate` for the one exact `RecoveryDecision` VM-start spawn; and latch-bound `ReliefGate` for exact stop/rollback/cleanup. No gate type can construct another scope.

Every forward gate acquires `emergency.lock`, rereads all durable relief requests, revalidates and consumes its typed capability, assigns an effect ID and exact target fingerprint, and fsyncs `EffectInFlight { scope, state: Prepared }`. While still holding that lock, `local` performs exactly one named atomic commit and records its resolved or indeterminate result; `spawn` starts exactly one already-constructed child in a dedicated process group, with `PR_SET_PDEATHSIG=SIGKILL` plus the post-`prctl` parent check, then records PID/start identity/process group and `state: Spawned`. It releases `emergency.lock` immediately after the commit or successful spawn and never waits, polls, sleeps, performs network I/O, reads child output, retries, or invokes an open-ended callback while locked. Wait/result/cancellation happens after unlock and atomically resolves the record. Because `emergency-stop` publishes and fsyncs its request under the same lock, ordering is linear: latch-first rejects without commit or spawn; gate-first permits at most its one recorded already-initiated primitive, which relief then cancels from the identity-verified process group, while every later forward gate rejects. No forward side effect can be initiated after durable latch publication; an already-submitted remote request is explicitly an indeterminate prior operation, not silently treated as undone.

All runtime and recovery roles derive one config- and receipt-independent containment root from the deploy UID's passwd home: `<deploy-home>/.local/state/ezgha-containment`. It is a non-symlink directory owned by that UID/GID with mode `0700`; environment variables and `config.state_dir` cannot relocate it. The canonical `serve.lock`, `emergency.lock`, relief request journal, transaction ownership records, and receipt-bound `handoff.sock` live only there. Configurable `state_dir` remains available only for runner ledgers, workspaces, quarantine, and other application data. Direct start/serve/stop, systemd private mode, transaction, handoff, emergency stop, transaction recovery, and receipt-independent clearance all open the same containment-root paths. A non-default application `state_dir` therefore cannot create a second admission fence, handoff namespace, or relief namespace.

Death at `Prepared`, `Spawned`, or after a local commit leaves a durable indeterminate record that is never generically replayed. Read-only outcome proof either resolves it or applies scope-specific fail-closed handling: admission quarantines the slot/runner; deployment leaves the transaction `RecoveryRequired` or direct deployment `Mixed`; recovery never respawns the VM and only reclassifies its exact endpoint. The shell installer performs read-only checks and writes staging files only; Rust's deployment executor uses `DeploymentGate` separately for every live artifact rename, policy/unit commit, manager reload/enable, and candidate/compatible-rollback start spawn. Exact rollback restoration, service stop, and manager reload after a latch use `ReliefGate`, may not start anything, and retain the same no-wait-under-lock rule. All Docker/GitHub launches and runner-ledger/quarantine/workspace commits are private behind `AdmissionGate`; the one pre-daemon VM start is private behind `RecoveryGate`. Test-only fakes use the same interfaces. A newer successful observation generation does not change the revocation epoch or invalidate a live permit. `PolicyFailed`, `StaleSince`, boot-ID change, or metadata mismatch increments the epoch and revokes all older admission permits. A serialized ten-runner refill may therefore remint from successive healthy snapshots for more than 300 seconds, while drift between any two automatic side effects blocks the next one.

`ReliefCleanup` is deliberately narrower and does not require healthy admission. Explicit `stop`, SIGTERM drain, `emergency-stop --confirm [--cancel-running]`, and compensation for one previously admitted JIT transition may remove only exact proven-owned local containers, registrations, and ledger rows. JIT compensation uses an unforgeable in-memory `TransitionReceipt` bound to the admitted transition ID, exact runner ID, slot, and already-completed side effect; it may finish exact ledger bookkeeping or undo that resource after revocation but cannot retry JIT, reserve another slot, run Docker, dispatch work, or refill. Relief cleanup never pulls/creates a container, starts/restarts a backend, dispatches or cancels unrelated work, or expands capacity; emergency cleanup makes no GitHub call. Automatic stale/quarantine/zombie reconciliation is not relief and remains admission-gated. Before automatic pre-start `docker rm -f`, Rust proves immutable managed label, configured slot/name, recorded runner ID, and local ownership; ambiguity skips removal and fails that start attempt.

Slot-ledger parsing is strictly read-only. A corrupt file returns typed `CorruptLedger` without creating a directory, renaming/truncating the file, or continuing reconciliation. Only a higher caller that already owns `AdmissionIssuer` may mint `AdmissionMutation::QuarantineCorruptLedger` immediately before one exact no-replace rename into a canonical quarantine path; after that repair it ends the current reconciliation without reserve/refill, so any later work requires a new iteration and fresh permit. Mint denial leaves the corrupt file untouched and performs no resource side effect. `AuditStateWrite` may still record the denial without carrying a mutation capability.

`ExpiredWhileHealthy` is local control flow: discard the permit and retry `mint_mutation()` once from the latest healthy snapshot. It does not increment `ensure_fail_streak`, call `notify_ensure_failure`, alert, pause the failure ladder, restart a backend, or withhold dead-man credit by itself. Only a remint result of `StaleSince` or `PolicyFailed` enters the failure paths below. Direct one-shot `start` has no background attestor; if its serialized reconciliation outlives the 45-second snapshot, it performs a fresh bounded full runtime admission between mutation boundaries before reminting and never reuses an expired permit.

`AdmissionControl` is an interrupt channel, not a replacement timeout policy. Healthy operations keep their existing deadlines, including the 45-second Docker command timeout, 120-second backend readiness/recovery budget, local readiness budgets, and 75-second queue-monitor budget. Foreground child-process helpers accept both their unchanged deadline and the control token and wait for normal completion, normal timeout, or explicit cancellation. Cancellation terminates the child process group, waits a bounded grace period, then force-kills descendants if needed; it returns a typed cancellation rather than an ordinary timeout. Sleeps and polling waits checkpoint at most once per second. The full-attestation worker alone retains its independent 15-second read-only deadline.

`PolicyFailed` is hard cancellation: the attestor publishes evidence, increments the revocation epoch, emits one cooldown-deduplicated critical alert, and requests foreground cancellation. `serve` checks control at the top of every settle/reconcile/monitor iteration, before and after external operations, and before each runner mutation; the first observed hard cancellation exits `78`, and no worker calls `process::exit`. Child-group cancellation plus one-second checkpoints make the 15-second policy-failure exit bound enforceable without shortening healthy-operation budgets.

A transient refresh may use the last successful snapshot until its 45-second expiry. `StaleSince` initially closes every new `AdmissionMutation`: it rejects every `mint_mutation` but does not cancel already-running read-only monitor/readiness work or an explicit `ReliefCleanup`. The first foreground observation emits dedicated cooldown-deduplicated `containment.attestation.stale`; each observation may also advance `ensure_fail_streak` and `notify_ensure_failure` as supplemental escalation. On the second denied foreground observation or 75 seconds after `StaleSince`, control escalates to transient hard cancellation and `serve` exits `75`. A fresh successful attestation before escalation clears stale state; an expired local permit that remints successfully is not a stale observation. Tests inject clocks, cancellation-aware fake operations, and spies; live evidence requires full-check rank-99 at or below 5000 ms and subprocess-free fast-guard rank-99 at or below 100 ms.

The deployment transaction must first receive successful static and dynamic install verdicts before image acquisition or live mutation, then stage policy, non-unit receipt artifacts, and unit candidates while holding the transaction lock. The Rust deployment executor is the sole privileged live writer: it revalidates the receipt-enumerated staging manifest and routes each final commit, mode/owner change, policy/unit removal, and manager reload/enable/start spawn separately through `DeploymentGate`. Deferred `install-service` independently obtains and consumes `TransactionAdmission`; ordinary direct installation obtains `RuntimeAdmission`. Rollback, stop, restore, and reload after a latch are separate `ReliefGate` effects and never start a service. Ordinary admission must then pass every final receipt path before descriptor handoff or start. Shell assertions and staging remain defense in depth; they do not own a second decision table, run privileged manager mutations, or write final paths. Host Docker never invokes VM/Lima recovery, even when a check fails. A failed check returns a typed diagnostic and performs no admission-side Docker, service, config, or live-limit mutation; the sole pre-admission mutation exception is an exact configured Colima/Lima start authorized by a successful static verdict and separately consumed by `RecoveryGate`.

Pre-daemon recovery is not admission. `RecoveryDecision` is the sole backend-start authority. Derived only from the static-validated proposed endpoint during installation or the persisted normalized endpoint at runtime plus the platform, it may be consumed once by `RecoveryGate` to spawn one bounded start of the exact explicitly configured stopped Colima/Lima backend and is never retried by a generic restart loop. The gate shares relief-latch linearization and registers the child before unlock; latch-first starts nothing, while gate-first exposes at most that one group for cancellation and never respawns an indeterminate result. It cannot restart an already-running VM. Canonical host, Docker Desktop, remote, inherited-context, indeterminate, and unsupported-platform endpoints produce `NoRecovery`; a stopped Docker Desktop daemon therefore returns a typed transient dynamic-preflight failure and is never auto-started. After a permitted VM start, full classification and `RuntimeAdmission` are still required before pre-pull or runner reconciliation. Outside a deployment transaction, durable pressure relief remains `systemctl --user stop ezgha.service` followed by ordinary `ezgha stop`; container removal alone is temporary while a supervisor can refill. Transaction-held relief uses the explicit fenced path below.

### Upgrade admission fence

The private Rust install transaction must quiesce the currently installed supervisor before image acquisition or any config, helper, receipt, policy, service-manager, Docker-runner, or GitHub-runner mutation. One tracked root-owned broker is installed at `/usr/local/libexec/ezgha/ezgha-privileged`, with exact mode `0755`, through the administrator bootstrap described below. It accepts only `transaction`, `recover-transaction --confirm-transaction <nonce>`, and `clear-relief --confirm-request <id>`; it accepts no path, shell command, or caller-selected environment input. Root-owned non-symlink `DeploymentBundleAuthorizationV1` metadata binds `schema`, broker protocol/digest, deploy UID/GID, passwd-derived containment root, fixed inbox identity, and one canonical `bundle_digest`. Its canonically sorted `entries` bind every transaction input/effect: role, `install|replace|remove`, exact final target, staged relative name, SHA-256 or required absence, mode, owner/group, and expected-prior fingerprint plus manager state for destructive operations. The bundle covers the candidate, config, receipt inputs, every helper/script/policy/drop-in/unit/generated-unit byte, every retired/remove target, and the tracked runner-image lock. A canonical `runner_image` record inside the bundle digest binds an immutable `ghcr.io/...@sha256:<64-hex>` reference, source commit, Dockerfile/context digests, and publisher provenance from that lock. Host deployment never builds or tags a runner image and rejects mutable tags or an untracked image reference.

For `transaction`, the broker opens the authorization, manifest, and every staged entry from that fixed inbox without following symlinks. It requires exact canonical equality between manifest and root authorization with no missing, extra, duplicate, reordered-ambiguity, target, operation, metadata, expected-prior, or `runner_image` difference; verifies every retained descriptor against the authorized bundle digest; and commits only the already-verified retained bytes without reopening an artifact pathname. An authorized candidate paired with a substituted config, helper, policy, unit, image lock/reference/provenance, removal operation/target, owner/mode, expected-prior fingerprint, or manifest therefore produces zero state, lock, gate, Docker, backend, manager, or final-path effects. Pathname replacement after verification cannot alter committed bytes. After fencing, the broker downshifts one exact digest-qualified `docker pull` to the deploy UID through `DeploymentGate`, verifies the requested repo digest and resulting local image ID, and records both in the receipt; runtime launches use that receipt-bound ID. It never invokes `docker build`, `docker tag`, or a checkout path. A wrong pulled digest, tag-only result, or later tag/image substitution blocks before runner work. The broker itself executes the closed Rust transaction state machine; it never root-executes the staged candidate. The candidate is installed only for later deploy-UID execution by the user service after receipt validation and handoff. `install.sh` performs preflight and local staging of the complete bundle, then ends with exact `exec sudo -n -- /usr/local/libexec/ezgha/ezgha-privileged transaction`; it does not retain a second shell control loop or prompt interactively. A missing helper, authorization, manifest, descriptor, role, or bundle mismatch exits fail-closed with zero effects. Normal transactions never replace the broker or authorization; any bundle content, metadata, target, operation, expected-prior state, runner-image lock/digest, broker protocol, or candidate change requires restaging and the tracked interactive bootstrap before quiescence. After both read-only install verdicts pass and prior state is snapshotted, Rust briefly acquires the canonical containment-root `emergency.lock`, rejects any durable relief latch, and releases that control lock before stopping `ezgha.service` or waiting. It records the old service's active/enabled state, stops only `ezgha.service` when active, and requires `ActiveState=inactive` and old MainPID exit within 30 seconds without holding either lock. It then reacquires `emergency.lock`, rechecks every durable latch, and only on success atomically publishes a mode-`0600` `Preparing` record with schema/generation/nonce, transaction-owner PID/start identity, boot ID, canonical containment-root lock path, config fingerprint, and prior service state. It releases the control lock before attempting the runner fence and never waits for `serve.lock`, service stop, or process exit while holding `emergency.lock`. It opens and retains an exclusive `flock` descriptor within 15 seconds for the fixed containment-root `serve.lock`; after acquisition it transitions the same nonce to `Fenced` with actual device/inode. Any relief latch found before `Preparing`, during fence acquisition, or afterward instead moves the state to `ReliefLatched`, permits no new mutation or later start, and leaves the service inactive. Static-verdict JSON supplies the canonical containment root and normalized application state path; the shell never reimplements either resolution. Managed/legacy upgrades must preserve application `state_dir`, target/scope, runner prefix, and immutable runner-image reference. Release builds remove `EZGHA_SKIP_LOCK`, retaining injection only under `cfg(test)`.

Stopping the supervisor does not cancel a running job. Managed-upgrade containers already proven beneath `actions.slice` may remain while the fence prevents refill. A legacy migration whose containers are not beneath the target aggregate performs a fixed 30-minute drain while holding the lock: it never cancels a busy job, waits for busy containers to finish, removes only idle managed containers/registrations, and requires zero legacy containers before policy mutation. The private Rust transaction opens a fixed inheritable descriptor, explicitly clears `FD_CLOEXEC`, acquires the exclusive lock, and passes its number only as `--transaction-lock-fd <n>` to its Rust drain and deferred-service child entrypoints. Before the first mutation, each child bounds-checks the descriptor, uses `fstat` to match it to a freshly opened canonical lock file, calls nonblocking exclusive `flock` on the inherited descriptor and requires success, then opens a second description and requires its nonblocking exclusive lock to fail with `EWOULDBLOCK`. The call is idempotent because the shared open-file description already owns the lock and rejects a third-party owner. No transaction child unlocks or closes the inherited descriptor, so the Rust transaction retains ownership after a child exits. Wrong inode, closed or exec-lost descriptor, or missing second-description contention is rejected before mutation. A drain timeout restores prior bytes before containment/config/helper/image mutation; descriptor-handoff-capable prior state may restore enabled/active state through reserved transfer, while pre-baton state records prior intent but remains disabled and inactive `RecoveryRequired`.

During the transaction, `install-service --defer-start --transaction-lock-fd <n> --unit-candidate-dir <path>` is accepted only with that validated inherited FD plus fresh `TransactionAdmission`; it validates receipt-bound staged bytes, atomically installs and verifies both units, but cannot start them. Final start transfers the existing locked open-file description; it never releases and reacquires the fence. A private Rust `handoff-service --transaction-lock-fd <n>` helper revalidates that inherited descriptor, then sets and verifies `FD_CLOEXEC` on its own descriptor copy before spawning any child. The flag is descriptor-local, so it prevents `systemctl` or descendants from inheriting the fence without changing the shared open-file-description lock or later `SCM_RIGHTS` transfer; the transaction-owner descriptor flag is unaffected. Before binding, the helper requires the canonical containment root to be the non-symlink directory owned by the deployment UID with exact mode `0700`; `init` creates it with that mode and installation rejects rather than trusting a group/world-writable or foreign-owned directory. The helper creates a fresh mode-`0600` Unix socket at `<containment-root>/handoff.sock` without following or replacing an existing path and publishes `HandoffReserved` under the containment-root `emergency.lock`. The reservation binds a random handoff nonce, transaction nonce, boot ID, transaction/helper PID-start identities, `connect_deadline_boottime = reserve_time + 25 seconds`, protocol version, socket path and identity, candidate-or-rollback mode, expected unit name, and exact binary/config/receipt/unit digests. Submission, assertion, provenance, claim, and connect are sub-budgets of that 25-second deadline. A successful `HandoffClaimed` records `ready_deadline_boottime = claimant_entry_boottime + 120 seconds`, covering peer proof, FD transfer, cleanup, runtime admission, `ServiceOwned`, pre-pull, and `READY=1` without additive extensions. The normative timing table defines calibration, boundary behavior, and the 145-second worst case within `TimeoutStartSec=210`; neither deadline is refreshed by retry, rollback, or state transition. The generated wrapper always execs hidden `serve --systemd-private`; plain `start` or `serve` has no claim path.

Private mode first performs common read-only systemd provenance within one five-second aggregate manager-query budget: environment `INVOCATION_ID` is exactly 32 lowercase hexadecimal characters and equals `systemctl --user show ezgha.service -p InvocationID`; `MainPID == getpid()`; manager `ControlGroup` equals the path obtained by stripping the exact leading `0::` from the unified-v2 entry in `/proc/self/cgroup`, and that normalized path ends in exact `ezgha.service`; `FragmentPath` equals the receipt-bound installed unit path; and `/proc/self/exe`, the CLI config path, and receipt-bound binary/config/receipt/unit modes and digests match installed state. A matching reservation additionally requires the reserved identities and live transaction-owner/helper identities before CASing `HandoffReserved -> HandoffClaimed`, then connects to the reserved socket and sends nonce, PID/start identity, and invocation ID. With no transaction, nonterminal handoff, or relief latch, private mode instead acquires `serve.lock` normally, runs the shared terminal-owner resolver below, rechecks state, obtains full runtime admission, publishes new ordinary ownership, pre-pulls, and emits `READY=1`. Direct `start` and `serve` use that same post-lock resolver before backend access. Any nonterminal, stale, malformed, or mismatched state not explicitly resolved below exits `78` and never falls through.

`ServiceOwned` always records boot ID as well as PID/start identity, invocation ID, lock identity, admission/artifact digests, socket-cleanup evidence, and typed origin: handoff origin includes transaction nonce plus fixed ready deadline, while ordinary origin records its owner-start boot time and no handoff deadline. The shared terminal-owner resolver runs only while holding canonical `serve.lock`, with the handoff socket absent and no transaction or unresolved relief request. It reads one generation under `emergency.lock` and performs at most one exact CAS: no terminal record proceeds after rechecking blockers; a syntactically complete, receipt-matching different-boot record is conclusively dead and archives as immutable `ArchivedServiceOwned { reason: PriorBoot }`; a complete same-boot record whose PID is absent or whose `/proc/<pid>` start identity differs archives as `ArchivedServiceOwned { reason: SameBootDead }`. Either archival additionally requires the manager unit inactive, except that the current private systemd caller may prove `MainPID == getpid()` plus matching invocation/cgroup provenance; a direct caller never archives around a foreign active unit. A current-boot record whose PID/start identity and all manager invocation, MainPID, cgroup, lock, and receipt evidence identify a live owner remains unchanged and exits `78`; because the caller holds an independently opened exclusive lock, contradictory live-owner/lock evidence also fails closed. Malformed, missing-boot, invalid origin/deadline, live-but-incomplete, artifact/lock/invocation mismatch, residual socket, failed CAS/fsync, or a foreign active manager never archives or starts; only a separately valid transaction snapshot may atomically record `RecoveryRequired { cause: TerminalOwnerEvidenceInvalid }`, otherwise the original bytes remain. An archival CAS fsyncs state and parent, then rechecks every blocker before full runtime admission; one CAS conflict restarts resolution from the new generation once, and a second conflict exits transient `75`. Archived state is audit-only and cannot authorize mutation. Ordinary systemd restart, direct `start`, and direct `serve` must publish a new boot-stamped ordinary `ServiceOwned` before pre-pull. Fixtures cover clean same-boot restart, reboot with PID reuse, live owner, contradictory lock evidence, foreign active MainPID, malformed/missing boot ID, invalid origin/deadline, residual socket, snapshot-backed recovery, and concurrent direct/systemd starts.

The handoff helper submits exactly one `systemctl --user start --no-block --job-mode=fail ezgha.service` through `DeploymentGate::spawn` while retaining the locked FD. The gate holds `emergency.lock` only through latch recheck, prepared-record fsync, and the exact child spawn/identity record, then releases it before the five-second executor waits. The helper accepts one connection and requires `SO_PEERCRED` PID/UID plus `/proc/<pid>` start identity, cgroup, executable, config, invocation, nonce, and receipt evidence to equal the matching `HandoffClaimed` state. It sends the already-locked FD over that connection with `SCM_RIGHTS`. The claimant calls `recvmsg(..., MSG_CMSG_CLOEXEC)`, rejects ancillary truncation, extra/missing descriptors, or an FD without verified `FD_CLOEXEC`, then bounds-checks and `fstat`s the received descriptor against a freshly opened canonical lock path. It requires idempotent nonblocking exclusive `flock` success on the received shared open-file description and `EWOULDBLOCK` from an independently opened description, then CASes `HandoffClaimed -> HandoffLocked` with the lock identity and sends an `FD_ACCEPTED` acknowledgment. Only after the helper verifies that acknowledgment and state may the Rust transaction close its inherited copy. The lock therefore remains continuously held by the same open-file description, no direct process can acquire it between transaction and service, and later Docker/GitHub children cannot inherit and strand the received lock.

Socket-path cleanup is part of the protocol, not best-effort housekeeping. After validated `FD_ACCEPTED`/`HandoffLocked`, the helper closes its listener, requires `lstat(<containment-root>/handoff.sock)` to match the reserved socket device/inode/type, unlinks only that identity, fsyncs the containment root, verifies the path absent, and sends `CLEANUP_COMPLETE` on the accepted connection before reporting handoff success. The claimant must receive that nonce-bound completion and independently prove the reserved path absent before it may publish `ServiceOwned`. If the connection closes or times out first, the claimant may complete the same identity-checked unlink/fsync/absence proof only after proving the reserved helper PID/start identity dead, which also proves its listener closed; a live or unproved helper leaves `RecoveryRequired`. A mismatched replacement is never removed and yields `RecoveryRequired`. Rust transaction success requires the socket path absent. On any failed handoff, matching socket unlink/fsync occurs only after no new peer can connect and any transferred receiver FD has been proven closed.

Submission timeout, signal, transport error, or an unproved rejection is ambiguous. Before any FD transfer, matching `HandoffReserved` becomes unclaimable `SubmissionUnknown`; a fully matching claimed/connected peer may finish the bounded transfer, while a latch, mismatch, failed peer proof, or other state becomes `RecoveryRequired`. No FD is sent after a latch or invalid proof. Failure before a validated ACK closes the socket but retains the Rust transaction's fence until state is unclaimable; it then closes the fence, performs bounded job/unit queries and stop without either lock, verifies inactive/MainPID exit, and reacquires `serve.lock` before rollback. After FD transfer but before `ServiceOwned`, failure or relief stops the service without either control lock, waits for its received FD to close, then reacquires and verifies the fence before rollback. A failure to stop, verify closure, or reacquire stays `RecoveryRequired` and starts nothing.

The claimant holding the transferred FD rechecks nonce/digests/latch and both fixed boot-time deadlines and obtains ordinary runtime admission. Only after `CLEANUP_COMPLETE` plus its own absence proof, or the dead-helper fallback proof above, and before pre-pull or any runner mutation, it CASes `HandoffLocked -> ServiceOwned` under `emergency.lock`, recording boot ID, PID/start identity, invocation ID, lock identity, admission evidence, artifact digests, socket-cleanup evidence, and the fixed ready deadline. `ServiceOwned` is terminal ownership: its publication proves that no reserved socket path remains, a live matching service survives transaction-owner death, and recovery cannot roll it back while its MainPID/invocation/lock evidence remains valid. `READY=1` is permitted only after pre-pull and a final latch/deadline recheck. Deadline expiry or any other failure after `ServiceOwned` but before READY first CASes that exact live ownership to `RecoveryRequired`, then closes without runner mutation and enters the bounded stop/reacquire path; neither deadline is refreshed. Rust transaction bookkeeping and READY polling are observational and hold neither lock. If the transaction owner dies before transfer, the service refuses; after transfer, the fully proven claimant may complete ownership, otherwise it records `RecoveryRequired`, closes the FD, and exits without runner mutation.

Queue rejection, peer/transfer/ownership/READY timeout, identity mismatch, or pre-ownership service failure follows the same stop, FD-close verification, fence reacquisition, and rollback sequence. A rollback restart is supported only when the prior receipt and wrapper advertise the same descriptor-handoff protocol version and bind exact prior artifacts; rollback uses an identical reserved socket transfer. Pre-baton or unproven legacy rollback restores byte-exact artifacts, records prior enabled intent, but leaves `ezgha.service` disabled and inactive with `RecoveryRequired`; unreserved rollback start and production lock bypasses are forbidden. Direct `install-service` remains runtime-admission-gated outside a transaction.

Rust-owned `ezgha emergency-stop --confirm` is the only production relief command that bypasses `serve.lock`. Under `emergency.lock` it atomically creates and fsyncs a durable mode-`0600` `ReliefLatched` request with schema, request ID, timestamp, boot ID, optional observed transaction nonce/generation, operator intent, and digest, and snapshots every registered `EffectInFlight` child process group after rechecking PID/start identity; it then releases the lock before signalling, waiting, or cleanup. The latch is never automatically deleted, ignored, or weakened because its nonce is absent, stale, mismatched, or malformed. Every direct `start`, `serve`, `install-service`, generated startup gate, transaction phase, handoff claim, and forward effect gate checks for any unresolved latch and fails closed before backend/service/runner mutation. A transaction records the request ID/digest, rolls back already-applied bytes under the fence through `ReliefGate`, leaves the service inactive, and never performs candidate or rollback start while latched. Repeated requests are retained as distinct IDs or an atomically auditable list. `--cancel-running` remains separately required for removal; without it, no running container is deleted. `ReliefCleanup` uses the latch-bound `ReliefGate` with the same no-wait-under-`emergency.lock` rule and cannot clear or reinterpret an in-flight forward-effect record.

The emergency command may stop `ezgha.service`, but never starts/restarts a backend or service, registers/refills/creates a runner, changes policy/config/receipts, calls GitHub, deletes registrations, or releases slots. With `--cancel-running`, it removes within a 30-second total deadline only a container whose inspection proves all of: label `ezgha=managed`, valid label `ezgha.runner_id`, exact configured slot/prefix name, and runner ID equal to that slot's persisted assignment. Inspect failure, empty/invalid assignment, label/name mismatch, ambiguous ownership, or sibling-host evidence causes a skip. Partial removal returns a distinct incomplete-relief result with removed, skipped, and failed IDs. Docker inspect and approved `docker rm -f` are the only backend operations allowed; offline GitHub registrations remain for the normal reaper after the transaction is gone.

Before and after every bounded transaction operation, before deferred unit install, before publishing/claiming/releasing a handoff, and at least once per second during legacy drain, the current actor checks the durable latch under `emergency.lock`. Latch acknowledgment atomically changes transaction state to `ReliefLatched`; no runner-capable operation begins after that point. A latch arriving before `Preparing`, while the fence is free or busy, during any handoff phase, or immediately before `READY=1` remains durable and blocks start/admission. If candidate service already started, emergency stop stops it; rollback completes only to an inactive state and does not reserve a rollback start.

`emergency-stop` waits at most 35 seconds for acknowledgment and reports incomplete relief after its bounded service-stop attempt on timeout; every request remains durable. Recovery has two tracked forms, neither of which starts anything. Non-emergency `./install.sh --recover-transaction --confirm-transaction <nonce>` validates syntax and ends with `exec sudo -n -- /usr/local/libexec/ezgha/ezgha-privileged recover-transaction --confirm-transaction <nonce>`. The fixed broker validates its own root-owned digest/metadata plus the exact receipt-bound installed-binary identity, then executes the closed recovery state machine itself; it never root-executes the installed application binary. Missing noninteractive privilege or missing/path-mode-digest-mismatched helper, metadata, receipt, or binary evidence fails before quiescence, locks, or live mutation. Only then does the broker acquire canonical `serve.lock` without holding `emergency.lock`, reject any unresolved relief request, require `ezgha.service` inactive, prove no live transaction/service owner by boot ID plus PID start identity, and accept only matching `Preparing`, `Fenced`, `HandoffReserved`, `HandoffClaimed`, `HandoffLocked`, `SubmissionUnknown`, or `RecoveryRequired`. It completes and verifies the saved byte-exact rollback or proves no mutation, fsyncs a terminal `RecoveredInactive` archive, removes stale handoff socket state, and leaves the service disabled/inactive when prior artifacts are pre-baton. That terminal state permits a later clean transaction retry; it does not authorize the old service to start.

Relief clearance uses `./install.sh --clear-relief --confirm-request <id>`. It performs no build, checkout lookup, config read, or receipt validation; after validating only the request-ID grammar it ends with `exec sudo -n -- /usr/local/libexec/ezgha/ezgha-privileged clear-relief --confirm-request <id>`. The already-installed fixed broker validates its own root-owned path/mode/digest and metadata, then opens only the passwd-derived canonical containment root, `serve.lock`, `emergency.lock`, transaction ownership records, and relief journal. It requires `ezgha.service` inactive, nonblocking exclusive `serve.lock` acquisition, no live owner, and the exact request ID/digest, then tombstones only that request and fsyncs the collection. It cannot build, read config or receipts, open transaction snapshots or deployment artifacts, invoke Docker/GitHub, start/reload/restore a manager, or accept arbitrary path, command, or environment input. Other unresolved requests remain durable. Clearing a latch never makes damaged or `Mixed` deployment state admissible: ordinary startup and receipt-bound transaction recovery still perform their full independent checks and remain blocked until repaired. A missing or invalid broker fails closed and is repaired only by the tracked administrator bootstrap; clearance never falls back to Cargo or a mutable checkout. Normal `ezgha stop` remains serialized by `serve.lock`; ordinary migration drain never invokes emergency cancellation automatically.

On the fixed Linux profile, the deployment receipt records the final config artifact's path, mode `0600`, SHA-256, and parsed `runner.count`; both the receipt and receipt-validated config must equal `10`. Direct `ezgha start` resolves `requested_count = --count.unwrap_or(config.runner.count)` and rejects with policy status `78` unless `requested_count == receipt.runner_count == config.runner.count == 10`. `--count 10` is accepted but is not an override. Rejection occurs immediately after config load and before lock acquisition, backend selection, containment admission, Docker/GitHub/systemctl invocation, ledger access, or any write. After acquiring the lock, ordinary full runtime admission repeats config identity/count validation to close the pre-lock race. Non-Linux legacy profiles preserve existing configured-count behavior. Runtime attestations and permits bind the persisted count, so no internal caller can expand the profile under a valid permit.

### Backend topology

Host Docker at `unix:///var/run/docker.sock` is an allowed production backend. It is not described as VM-contained. Add a backward-compatible defaulted `[backend].docker_endpoint` field to the deny-unknown config schema. New Linux install/admission requires a recognized explicit value and rejects missing, inherited-only, remote, or ambiguous endpoint state; `ezgha init` persists the normalized recognized endpoint it classified. One endpoint-aware `BackendTopology` classifier, owned by `src/backend.rs` and exposed as structured `ezgha topology --json`, combines that persisted endpoint with Docker daemon metadata: the canonical host socket plus a same-kernel Linux daemon is `HostDocker`; a recognized explicit Colima, Lima, or Docker Desktop socket plus VM daemon metadata is `VmDocker`; contradictory metadata, remote endpoints, and unknown sockets are `Indeterminate`. `Platform.daemon_in_vm` is only one metadata input and is never the classifier by itself. Shell gates consume the structured Rust result and do not duplicate the endpoint decision table. A Linux install/start gate rejects `Indeterminate`, while existing Mac and pre-existing runtime paths preserve their non-fatal warning/no-op behavior.

Legacy Mac configs without `[backend].docker_endpoint` use a Darwin-only compatibility resolver until their next `ezgha init` or `install-service`. It considers, in order, a nonempty explicit override, the installed launchd plist endpoint, the active Docker context, and recognized Colima/Lima/Docker Desktop sockets; it accepts only one normalized consistent endpoint and returns `Indeterminate` on disagreement, unknown transport, or no evidence. The resolved endpoint is persisted atomically during `init`/`install-service`; after persistence the config value overrides ambient state. A uniquely proven Colima/Lima endpoint retains the existing bounded recovery, while Docker Desktop, ambiguity, or missing evidence produces `NoRecovery` and never invokes Colima/Lima. This compatibility resolver is forbidden on Linux.

The generated unit always emits the config endpoint, including `unix:///var/run/docker.sock`, and clears inherited `DOCKER_CONTEXT`; every Rust Docker subprocess uses that same value and removes `DOCKER_CONTEXT`. The generated Linux service has no unconditional `lima-vm@colima.service` dependency, and backend recovery must never start Lima for `HostDocker`; a failed HostDocker permit is a hard no-op, never a VM recovery request. Only explicit Colima/Lima endpoints may use the existing bounded recovery path; Docker Desktop is classifiable when reachable but is non-recoverable by this implementation when stopped. An inactive legacy Lima unit may be disabled after the backend endpoint is proven; no VM disk is deleted.

For the `HostDocker` branch, the service may start only after the containment preflight establishes all of the following; `VmDocker` reports this host profile as not applicable and proceeds only through its separate VM gate:

1. The configured endpoint is exactly the canonical host socket, not a Colima/Lima or remote endpoint.
2. Docker reports cgroup v2 with the `systemd` cgroup driver.
3. The configured cgroup parent is `actions.slice`.
4. `/sys/fs/cgroup/actions.slice` exists under the system manager.
5. Its memory, swap, CPU, and task limits exactly match the declared fixed profile.
6. `actions.slice`, `agents.slice`, and `automation.slice` report both managed-OOM policies as `auto`; none has a production pressure threshold.
7. The deploy owner's `user@UID.service` is not actively monitored for memory pressure or swap, no production or ancestor root is enrolled with `kill` for either policy, and the broad service reports `ManagedOOMPreference=none` plus `OOMScoreAdjust=0` rather than a subtree-wide exemption.
8. The tracked finite `agents.slice` is effective and no unlimited local override is active.
9. Neither the installed `ezgha.service.d/10-oomd-omit.conf` nor its effective `ManagedOOMPreference=omit`/`OOMScoreAdjust=-1000` remains.
10. Unprivileged bounded `oomctl` queries work and list no production or broad desktop kill root during ordinary admission.
11. The host has at least 62 GiB RAM and 32 logical CPUs; this fixed hardware profile is rejected on a smaller machine instead of silently consuming its reserve.

Any failed invariant blocks new runner admission and emits a diagnostic naming the mismatched property. It does not restart Docker, Colima, the desktop, or the physical host.

## Components and Ownership

### Repository policy

`CLAUDE.md` owns the full crash-containment tenet. `AGENTS.md` contains a concise pointer because both files exist independently. `README.md` describes the user-visible topology accurately and stops claiming that Jeff-Ubuntu runners are inside Colima when host Docker is active. `/up` writes a short receipt under `roadmap/`.

### System policy artifacts

`systemd/host/actions.slice` owns the host runner aggregate. A separate top-level `systemd/host/ezghaproof.slice` contains `ezghaproof-hardlimit.slice` and `ezghaproof-oomd.slice`, so a synthetic proof is never a descendant of the production runner root. Fixed root-owned `ezgha-hard-limit-proof.service` and `ezgha-oomd-proof.service` units are the only proof launchers; they use a repository-owned Python-stdlib allocator, have no Docker socket or credentials, and cannot accept an arbitrary command. Hard-limit mode deliberately exceeds its child `MemoryMax`. Oomd mode allocates and continuously touches an anonymous working set above its child `MemoryHigh` but below `MemoryMax` for 75 seconds. Because systemd exposes pressure duration only as the global `DefaultMemoryPressureDurationSec`, the harness reads and records the effective merged oomd configuration and accepts only an unambiguous integral whole-second value in `1..=45`. Missing, malformed, zero, negative, fractional, unit-suffixed, or larger values fail. It requires the child's exact `memory.pressure` `full avg10` value to stay at least 20% continuously for that duration before accepting a correctly named journal victim. Allocator exit without both the continuous measured interval and victim never passes. The proof harness uses privileged `systemctl` only with those literal unit names and never permits `systemd-run` or a shell. The six tracked system/user drop-ins own the root, system-user, dynamic-user, user-manager, app, and session vendor-policy overrides. Existing `systemd/agents.slice` and `systemd/automation.slice` own user workload limits.

The proof-only oomd policy is intentional: Ubuntu's vendor `user@UID.service` kill behavior is the broad crash blast radius being removed, and system-wide swap selection among production roots could redirect that failure into agents or automation. All production and desktop roots are explicitly `auto`, and the user service is neutral rather than `avoid`/`omit` or negatively scored. `oomctl` must show no ordinary production or desktop kill root; only the isolated proof child may appear while the opt-in proof is active. That proof demonstrates isolated oomd semantics, not production enrollment or a global desktop-survival guarantee.

### Installation

`scripts/host/install-crash-containment.sh` is a nonprivileged reader/stager. It supports a read-only capability/current-use `--preflight`, a read-only installed-state `--check`, and a staging-only `--stage` mode that creates the complete canonical manifest and bundle tree in the fixed candidate inbox without `sudo`, service-manager mutation, or final-path writes. For normal installation, `install.sh` invokes the stager, requires the staged manifest/bundle digest to equal independent root-owned `DeploymentBundleAuthorizationV1`, and ends with `exec sudo -n -- /usr/local/libexec/ezgha/ezgha-privileged transaction`. It never uses `sudo -E`, a mutable sudo target, a shell command string, an interactive prompt, or a later privileged subprocess. The broker descriptor-validates the entire authorized bundle and runs the transaction itself; the candidate is never privileged and may execute only later as the deploy UID after receipt-bound installation and handoff. Recovery and clearance are also performed directly by the broker without root-executing application code; clearance needs no config, receipt, checkout, or toolchain. Missing noninteractive privilege fails before quiescence, locks, or mutation. Outside the explicitly classified administrator bootstrap, only the root-owned Rust broker may acquire transaction locks, mutate durable state, apply or roll back artifacts, or submit manager operations, and every live primitive is latch-linearized through `DeploymentGate` or `ReliefGate`.

After an allowed local candidate build, installation has two read-only phases. Static preflight first validates a mode-`0600` proposed config with an explicit endpoint, hardware, privilege, deployment state, and rollback storage without requiring a reachable VM daemon. The state classifier does not treat a config file alone as an upgrade:

- `Bootstrap` requires no receipt/helper set, generated user units, active/enabled runner service, managed-prefix container, or registered-prefix runner. The active config may be absent or byte-identical to the proposed config and is staged data, not deployment evidence; any partial runtime/policy artifact is `Mixed`.
- `ManagedUpgrade` requires a complete receipt, every receipt-listed artifact, both generated user units, the active config, and all expected effective cgroups. It enforces the current-use margins.
- `LegacyMigration` requires a recognized complete pre-receipt service/config/runtime signature. It is never adopted as fresh and must pass the upgrade admission fence plus bounded legacy-container drain.
- `Mixed` covers partial receipts/helpers/units/cgroups, an unrecognized differing active config, orphaned registered-prefix runners, or any other incomplete combination and fails before image, runner, policy, config, or service mutation.

A receipt whose unit entries exist only in the receipt-bound candidate directory is an allowed transitional state solely inside the running transaction while the validated exclusive lock is held. It is never a persisted deployment classification. After process interruption or without that exact lock/candidate proof it classifies `Mixed`, ordinary admission fails, and no service may start; rollback removes or restores the receipt and all listed artifacts.

A terminal `RecoveredInactive` archive is not itself deployment evidence and is not automatically `Mixed`. The classifier first verifies its transaction nonce, exact saved snapshot digest, completed byte-exact rollback, absent handoff socket, inactive service, and disabled state when restored artifacts are pre-baton, then classifies the restored artifacts normally as `Bootstrap`, `ManagedUpgrade`, or `LegacyMigration`. Any archive mismatch remains `Mixed`. A clean retry consumes/archives the recovery marker only after publishing its own new `Preparing` nonce.

This supports the documented two-pass bootstrap: the first `./install.sh` performs only `cargo build --locked --release` in the checkout and requests `target/release/ezgha init`; `init` may read endpoint/daemon metadata but cannot start/recover a backend or build/pull/run an image, writes only an explicit-endpoint starter config, and creates both the fixed canonical containment root and configured application `state_dir` as non-symlink deploy-UID-owned mode-`0700` directories. The second `./install.sh` treats that config-only state as staged `Bootstrap`. It does not replace the installed binary before preflight. Current `install.sh` config-presence auto-start/restart is removed; only the Rust containment transaction may atomically promote the candidate binary and call `install-service`. Every install/handoff rejects a foreign-owned, symlinked, or group/world-writable containment or application-state directory. Only a recognized explicit Colima/Lima endpoint may produce a one-use `RecoveryDecision`, and only Rust may consume it through `RecoveryGate` to start that exact configured VM between static and dynamic phases. Dynamic preflight then proves daemon topology, Docker cgroup v2 with the `systemd` driver, and unprivileged `oomctl`. Both phases precede admission quiescence, image acquisition/build/pull, and every installed/live mutation. Canonical host, Docker Desktop, remote, inherited-only, indeterminate, and unsupported-platform endpoints never recover a VM; a failed phase exits without image work or changing the installed binary, generated service, config, helpers, or live limits. The supported portable target is a fresh systemd Ubuntu host meeting the declared 62-GiB/32-CPU profile; scaled profiles are a separate reviewed design, not an implicit fallback.

The private Rust transaction installs and receipt-binds all six desktop-boundary drop-ins, removes the known `agents.slice.d/99-local-unlimited.conf` drift file and live `~/.config/systemd/user/ezgha.service.d/10-oomd-omit.conf`, disables and removes the obsolete `psi-oom-watcher` service/timer plus its installed stable script, and retires every independently scheduled mutating queue or agent-scope reaper plus the runtime `lima-vm-cpu-ceiling.service` `set-property` unit. The standalone cleanup/queue scripts and `ezgha reaper-plan` are read-only; only the lock-owning supervisor's private coordinator can apply a queue plan through `AdmissionMutation`. Rust reloads the appropriate managers without restarting the desktop or physical host and fails if a retired reaper or runtime property unit remains active/enabled. It verifies the exemption's unit configuration is gone before restart, then verifies the new MainPID's `/proc/<pid>/oom_score_adj` and effective properties after restart. Before lowering an active hard limit, it records `MemTotal`, `MemAvailable`, `SwapTotal`, `SwapFree`, `memory.current`, `memory.stat`, `memory.swap.current`, and `memory.swap.peak` for the actual workload roots; requires the fixed cap sum to leave at least 8 GiB arithmetic RAM reserve; and uses enforceable `memory.current` without discounting file cache to prove the 1-GiB actions, 1-GiB agents, and 512-MiB automation margins. Otherwise it leaves live policy unchanged and fails. The Rust transaction snapshots the installed `ezgha` binary bytes/path/mode/digest, live config, all replaced system/user policy and helper files, both generated services, the versioned deployment receipt and every receipt-listed artifact, all retired watcher/reaper/exemption/runtime-property artifacts, and applicable prior active/enabled state. After both read-only verdicts it performs the upgrade admission fence, then atomically installs the candidate binary, mode-`0600` proposed config, and helper/policy set. Any failure restores every file byte-for-byte and reloads both managers through typed gates. Receipt-proven descriptor-handoff state may restore enabled/active state through reserved transfer; pre-baton state records prior intent but remains disabled/inactive `RecoveryRequired` until verified recovery and a clean installer retry. Rust verifies effective restored state before returning failure, installs only persistent tracked units, never creates overriding `systemctl set-property` drop-ins, and never deletes VM data.
The Rust transaction also publishes a versioned deployment receipt atomically with final `config.toml`, the candidate binary, helper set, and staged generated-unit candidates. The receipt records the deployed source commit SHA, explicit `startup_handoff_protocol = 1`, and, for config, the binary, every helper, `ezgha.service`, and `ezgha-alert@.service`, the artifact role, candidate/source path, final installed path, exact mode, and SHA-256. Its required `runner_image` object records the exact digest-qualified GHCR reference, verified local image ID, SHA-256 of `config/runner-image.lock`, publisher source commit, and workflow/Dockerfile/context digests copied from the authorized lock. Protocol 1 means the bound wrapper uses the exact private entrypoint and the bound binary implements peer-proven Unix-socket `SCM_RIGHTS` transfer, helper-side and receiver-side close-on-exec, two-phase acknowledgment/cleanup, and fixed connect/ready deadlines; absent, unknown, or inconsistent protocol is pre-baton for rollback. The config entry additionally records parsed `runner.count` and image reference; fixed Linux requires mode `0600`, count `10`, and exact equality between config image, authorized lock reference, and receipt repo digest. Config, files, unit candidates, and image identities are staged or acquired, mode/digest/count/image-checked, flushed, and renamed before the receipt is renamed into place; a receipt that does not describe this complete deployment set is invalid. The transaction-scoped permit validates final config and installed binary/helpers plus staged unit candidates, allowing deferred service installation without circularly requiring new units to be installed first. After deferred installation, ordinary admission validates every final receipt path, mode, digest, parsed count, supported startup protocol, lock/provenance fields, exact repo digest, and current local image ID before descriptor handoff, pre-pull, or runner work. Missing or wrong image/lock/provenance fields, a repo-digest mismatch, absent/replaced local ID, or tag-only resolution fails closed. Runtime commands execute the receipt-validated config and installed immutable binary/helpers, launch only the receipt-bound local image ID, and never use a mutable checkout or tag as deployment evidence. The receipt and every artifact it describes are one rollback unit: bootstrap rollback removes them together, upgrade rollback restores their prior bytes together, and either path rejects partial state; an immutable image newly cached by a failed transaction remains inert because no valid receipt can authorize it.

### Startup preflight

`scripts/host/assert-crash-containment.sh` is a read-only executable installed under `~/.local/libexec/ezgha/`. The generated `ezgha.service` uses a tracked wrapper as `ExecStart`, passing exact receipt-bound binary/config paths. It runs canonical `containment-check --admission --json` plus the defense-in-depth assertion, propagates `75`/`78`, and on success executes exactly `exec "$binary" --config "$config" serve --systemd-private`. That hidden flag is accepted only with the systemd provenance proof above: a matching reservation enters descriptor handoff, while absence of transaction/handoff/latch enters ordinary serialized systemd startup. Plain direct `start`/`serve` cannot claim a transaction handoff. The assertion performs three Docker queries over at most 15 seconds; preserved restart/start-limit and `TimeoutStartSec=210` settings bound startup. Backend classification uses configured endpoint plus daemon metadata. Every final receipt path/mode/digest must match installed state, not checkout.

Service regeneration preserves failure alerting. The main unit retains `OnFailure=ezgha-alert@%N.service` plus a fail-open `ExecStopPost` that invokes the exact installed binary/config with `systemd-alert-hook --source exec-stop-post`. The companion `ezgha-alert@.service` remains a 30-second `Type=oneshot` invoking the same binary/config with `--source on-failure`; both units inherit the persisted endpoint and cleared Docker context, and both are included in transactional rollback tests.

The assertion returns distinct statuses for a proven policy violation and a transient inability to query Docker. The generated service permits recovery from a short transient failure within its existing bounded start window, while a proven policy violation remains fail-closed and clearly logged. This is normal service recovery, not a second repair daemon and never mutates containment policy.

### Verification

`docs/verify-exit-criteria.sh` verifies effective values rather than file presence. Host-Docker and Colima gates are mutually exclusive: the host path checks the system `actions.slice`, the `systemd` Docker cgroup driver, actual cgroup ancestry for every managed container, user workload caps, production/desktop managed-OOM `auto` policy, empty ordinary `oomctl` production roots, and the absence of unlimited/runtime overrides and `ezgha.service` OOM exemptions. It also validates the versioned deployment receipt against installed binary, helper, and generated-unit paths, modes, and digests. It does not include an inactive Lima slice in host-Docker budget arithmetic or require a live guest. Runtime, assertion, both doctors, and the verifier consume one canonical Rust topology result and replay the same tracked golden fixture corpus; raw Lima/QEMU inspection is diagnostic only and cannot produce another verdict. `doctor-runner` reports that topology without mutating it.

## Data Flow

1. `install.sh` may build the exact local candidate binary locally (the build cannot invoke Docker), requires a successful static install verdict, stages the complete canonical deployment bundle in the fixed inbox, proves its digest and every entry equal root-owned `DeploymentBundleAuthorizationV1`, proves noninteractive access to the fixed broker, and ends with exact `exec sudo -n -- /usr/local/libexec/ezgha/ezgha-privileged transaction`. The broker descriptor-validates and executes the transaction state machine itself; the candidate is installed for deploy-UID execution and is never root-executed. The broker classifies `Bootstrap`, `ManagedUpgrade`, `LegacyMigration`, or `Mixed`. For an explicit recognized Colima/Lima endpoint on a supported platform only, Rust may consume one exact `RecoveryDecision` through `RecoveryGate`, then requires the dynamic Docker-backed install verdict. Host Docker and Docker Desktop never recover a VM. Neither verdict is an admission capability.
2. After both verdicts and a read-only transaction snapshot, the Rust transaction stops the old supervisor, verifies it inactive, and holds canonical `serve.lock`; legacy containers drain without cancelling busy jobs. Both phases and admission quiescence must pass before image acquisition or any other config/helper/policy/runner mutation.
3. The Rust deployment executor copies tracked units and the root-owned proof allocator to their system and user destinations through separate `DeploymentGate` effects, atomically retires the old watcher and both source/live exemption state, reloads managers, and checks effective properties including `oomctl` roots.
4. After containment, deferred installation validates the inherited lock/staged receipt, consumes `TransactionAdmission`, and installs units without starting. Ordinary admission validates final artifacts. While fenced, the Rust handoff helper reserves and queues exact private systemd mode, verifies its claimed MainPID, and passes the continuously locked open-file description through `SCM_RIGHTS`; the claimant receives it close-on-exec and sends `FD_ACCEPTED` before the Rust transaction closes its copy, then proves listener closure/socket cleanup before recording boot-stamped terminal `ServiceOwned`, pre-pull, `READY=1`, or runner work inside fixed deadlines. With no transaction/handoff/latch, the same private wrapper takes ordinary serialized systemd boot/restart through exact dead-owner archival. Long-lived serve remints one-use admission before every latch-linearized `AdmissionMutation`; only exact `ReliefCleanup` bypasses healthy admission. Pre-ownership failure or relief latch restores inactive prior state unless compatible descriptor-handoff rollback succeeds; pre-baton rollback remains disabled/inactive, and live valid `ServiceOwned` is not rolled back after transaction-owner death.
5. The endpoint-aware topology enum controls budgeting: `HostDocker` ignores VM-only guest-reserve fields and delegates the aggregate ceiling to system `actions.slice`; `VmDocker` retains the existing guest reserve and VM envelope; `Indeterminate` is rejected by new Linux install/start gates while preserving the bounded legacy-Mac resolver.
6. `ezgha` creates each runner with `--cgroup-parent=actions.slice` plus per-container memory, CPU, PID, swap, and security limits.
7. The system manager accounts every runner beneath the finite aggregate.
8. Under ordinary pressure, `MemoryHigh` throttles and reclaims workload memory.
9. At the hard boundary, the kernel enforces `MemoryMax` within that limited cgroup. Only the separately invoked synthetic proof enrolls an oomd kill root.
10. Separate hard-limit, oomd-selection, ten-worker execution, and live desktop-survival proofs record what actually happened instead of inferring behavior from configuration.

## Residual Risks

- The approximately 8.5-GiB remainder (`62.48 - 54 = 8.48 GiB`) is not reserved memory. Docker, the kernel, desktop applications, and other system services remain outside the three hard caps and can still trigger global kernel OOM.
- Production does not use oomd to provide a runner-before-agent order; it relies on independent finite cgroup boundaries.
- `MemorySwapMax=0` avoids runner swap thrash, but uncapped desktop/kernel/system consumers can still exhaust global memory or swap; `MemoryMax` is the deterministic workload boundary.
- `CPUQuota=2000%` equals the ten configured 2-CPU container maxima and reserves 12 of 32 logical CPUs for the host; the capacity proof still checks real ten-job execution.
- Portable block-device bandwidth caps require a measured device baseline. `IOWeight=25` gives runner I/O lower relative priority where the controller is available; the verifier reports unavailable controllers rather than asserting protection.

## Failure Handling

| Failure | Required behavior |
|---|---|
| Host `actions.slice` missing or infinite | The main startup wrapper exits `78`; no new runners start and systemd does not restart the policy violation. |
| Static or dynamic preflight fails, or scoped admission is missing/expired/receipt-invalid | Preflight leaves live mutation unchanged except one exact statically authorized Colima/Lima start. Failed full admission blocks direct start, serve pre-pull, direct install, and direct canary dispatch; stale/revoked mint blocks the next automatic Docker/GitHub/ledger/quarantine/workspace/control side effect. `ExpiredWhileHealthy` remints without failure-ladder side effects; exact `ReliefCleanup` remains available. |
| Linux direct count differs from receipt-backed config or fixed value 10 | Exit `78` immediately after config load with zero lock, backend, containment, Docker, GitHub, ledger, or write operation. Full post-lock admission repeats the validation before reconciliation. |
| Background attestation proves policy drift | Increment revocation epoch, block the next mutation, alert once, cancel foreground child groups without changing healthy timeout policy, and exit `78` within 15 seconds. |
| Background attestation is transiently unavailable past snapshot TTL | Enter soft `StaleSince`, deny new mutation and alert on first observation; after two denials or 75 seconds hard-cancel and exit `75`. A fresh pass before escalation clears stale. |
| Handoff queue, peer, FD transfer, ownership, or READY fails | Before `ServiceOwned`, record `RecoveryRequired`, stop/wait inactive without locks, verify the received FD closed, and reacquire before rollback. A live valid `ServiceOwned` survives transaction-owner death. Compatible rollback repeats descriptor transfer; pre-baton rollback restores bytes but remains disabled/inactive and has an exact non-emergency recovery path. |
| Confirmed emergency stop at any time | Persist every `ReliefLatched` request even without matching transaction state. Direct/startup/handoff admission fails closed; an active transaction rolls back and leaves service inactive. Exact targeted clearance removes one request while others continue blocking; the final clearance never starts anything. Running containers require `--cancel-running` plus exact ownership proof. |
| Bootstrap/upgrade state is mixed, or upgrade quiescence fails | Installation fails before image or containment/config/helper mutation. If the old service was stopped, compatible state may restore through descriptor handoff; pre-baton state remains disabled/inactive and recoverable for a clean transaction retry. Busy jobs are never cancelled. |
| Docker query is temporarily unavailable | The assertion retries for at most 15 seconds and returns `75`; normal service restart retries at 30-second intervals and the existing five-start/300-second limiter stops a persistent outage. After fixing the prerequisite, the tracked runbook requires a passing `ezgha containment-check --admission --json`, then `systemctl --user reset-failed ezgha.service` and `systemctl --user start ezgha.service`; no monitor resets or loops the limiter. |
| One runner exceeds its limit | The cgroup-local OOM is contained to that runner scope. Whole-container exit is claimed only when effective `memory.oom.group` or observed exit behavior proves it. |
| Runner aggregate exceeds `MemoryHigh` | Reclaim/throttle occurs inside `actions.slice`. |
| Sustained runner pressure | `MemoryHigh` reclaims/throttles within `actions.slice`; a process in that finite cgroup is locally OOM-killed only if the hierarchy reaches `MemoryMax`. |
| Agent aggregate exceeds its envelope | Pressure handling remains within `agents.slice`; desktop survival is a live integration result, not a static guarantee. |
| `systemd-oomd` inactive | Production containment is unchanged because ordinary roots are `auto`; the isolated oomd proof is unavailable and cannot be claimed. |
| Host Docker selected while Lima unit is enabled | Verification fails with topology drift; installation may disable an already inactive Lima unit but never stops a live VM automatically. |
| System privilege, topology, driver, hardware, or `oomctl` preflight unavailable | Installation fails before mutation with the exact unmet prerequisite; it does not deploy a falsely green user-only approximation or restart the fleet. |
| Post-mutation verification or gated restart fails | Restore final config, system/user policy, binary/helper files, receipt, units, and retired watcher/exemption files. Restore enabled/active state only through receipt-proven descriptor handoff; otherwise verify byte-exact disabled/inactive `RecoveryRequired` rollback and its tracked recovery path. |
| Pressure proof harms the desktop or host | Test fails immediately and blocks deployment; no threshold is accepted from synthetic unit tests alone. |

Normal operation has no interactive sudo, mutable-checkout sudo target, shell command string, `SETENV`, or Cargo-dependent clearance.

## Implementation Preconditions

- Before a fresh deployment or any bundle/helper change, the nonprivileged stager builds the complete bundle, then an administrator runs the tracked bootstrap to descriptor-verify every entry and atomically install the fixed root-owned broker, `DeploymentBundleAuthorizationV1`, root-owned deploy metadata, and a user-specific mode-`0440` sudoers drop-in. The bootstrap verifies safe root-owned parent chains and the deploy account, validates the drop-in with `visudo -cf`, installs atomically with byte-exact rollback, and proves `sudo -n` can invoke only the broker's three exact grammars. This is the sole interactive privilege step; deployment, recovery, and clearance fail before quiescence if that contract is absent. User-only installation cannot enforce Docker's system cgroup hierarchy.
- The live deployment must follow the repository's single-writer checks before restarting `ezgha.service` or running the live harness.
- The bounded pressure proof requires privilege to start the two fixed tracked proof services by literal name; arbitrary transient units and commands are prohibited. The repository supplies the fixed bounded allocator rather than depending on `stress-ng` behavior.
- Live activation requires current usage to fit below each proposed `MemoryHigh` with the declared workload-specific margin: 1 GiB for actions, 1 GiB for agents, and 512 MiB for automation; otherwise deployment stops before installing or reloading units.
