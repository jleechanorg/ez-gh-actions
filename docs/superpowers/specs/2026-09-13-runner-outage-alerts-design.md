## Alternatives and decision

1. **Configure only existing daemon Slack/email:** smallest change, but it cannot report a stopped host or wedged serve loop, retains local-mail infrastructure, and misses independent script failures.
2. **Mac and Linux watch each other:** survives one daemon failure, but shared LAN/power failure silences both; adds SSH keys, duplicate incident ownership and network ambiguity.
3. **Recommended: one independent observer per host plus externally hosted heartbeat monitoring.** Reuse local observation code and native schedulers; route fleet health through hosted Healthchecks.io with Slack and verified email integrations on each host check. The external service detects missing heartbeats even if both machines or their network disappear. This is an architectural choice, not a claim an account/integration already exists.

No new Prometheus stack or LLM monitor is required. Fixed process observations and explicitly configured timing contracts are mechanical checks, not intent classification. Model judgment is not on the monitoring path.

## Architecture and ownership

`native host scheduler -> bounded local observer -> Healthchecks per-host check -> Slack AND email`

The observer is outside `ezgha serve`, outside Docker/Colima, and performs only local reads plus HTTPS heartbeat delivery. Exactly one scheduled observer owns each host check. Never schedule it on these GitHub runners. Use stable host IDs `mac-primary` and `linux-jeff-ubuntu`, independent of ephemeral prefix rotation. Validate count against the explicit fleet contract (Mac 6, Linux 10); config changes cannot silently shrink expected capacity.

Reuse and extend the dashboard host probe with a backward-compatible `--monitor` mode: resolve service-owned config and Docker endpoint, emit versioned JSON including every expected slot, and make all probes read-only and bounded. Existing dashboard behavior stays compatible. `scripts/ezgha-fleet-alert.sh` becomes a thin compatibility entrypoint for the Python standard-library observer; retire its competing scheduling/sink behavior during an explicit migration. Add a Linux oneshot/timer. The existing watchdog remains the recovery owner; the observer never restarts or repairs anything.

The hosted check is the sole new **fleet availability** delivery owner. Existing daemon alerts for distinct disk/registration/queue causes remain visibly named as diagnostic events. Linux OnFailure/ExecStopPost retain local failure diagnostics and may emit distinct cause events, but the migrated configuration disables their overlapping fleet-availability remote page; the hosted check alone owns daemon/host availability Down/Up. Preserve hook diagnostics when changing routing; migration documents any overlap. Do not duplicate fleet pages from both old shell sink and hosted check.

## Observations and failure semantics

Each sample records schema version, host ID, wall time, boot ID, sequence, configured and expected count/prefix, Docker endpoint identifier (not credentials), config validity, service state, Docker reachability, required image presence, per-slot `EXECUTING|IDLE|DOWN|UNKNOWN`, daemon progress sequence/stage/time, and bounded error codes. Evidence comes from `docker ps/inspect/top` against the exact endpoint. Reserved assignments never satisfy capacity. A failed/timed-out Docker call produces UNKNOWN, never zero healthy or a healthy empty list.

A lightweight daemon progress record is written atomically by `src/main.rs` after completed reconciliation/monitor stages, including boot ID, sequence and last-progress time. It must never be refreshed by a timer independent of completed work. A live PID with progress older than 120 seconds is a direct fault under the two-sample rule; an absent, invalid or future-dated record is UNKNOWN and faults similarly. Stage deadlines must remain below this progress bound; verify actual stage budgets before activation. This catches an active-but-wedged serve loop even when existing containers still have Listeners/Workers.

Monitor capacity and execution as separate properties. Full execution proof always requires Worker evidence for every configured slot. Healthy availability can include listeners when there is no eligible work. IDLE-STARVED requires a queue snapshot <=120 seconds old proving eligible queued work for the same labels/host; pending approvals, concurrency locks, unrelated routing, and arbitrary run counts are not proof. Derive each host's authoritative label set from the service-owned runner configuration (including configured custom labels) and its verified registration-label projection; Docker containers hosted on the Mac are not necessarily native macOS runners. Persist a versioned mapping of host ID to these exact labels, config digest and evidence time. Never infer host routing from the runner-name prefix alone. Jobs matching both hosts' labels belong to a shared pool and cannot establish starvation on one particular host without additional job/runner correlation; mark that host assignment UNKNOWN. Generic `self-hosted` alone cannot prove Mac or Linux eligibility. Reuse existing structured job correlation, not title matching.

The current default queue producer is disabled/300-second cadence and other snapshots can be 240 seconds old, so it does not meet the freshness contract. Implement the queue producer as one dedicated worker thread started by the Linux daemon, with its own 60-second schedule and shutdown signal; it never waits for serve-loop completion. In this mode the old serve-loop queue fetch is disabled and consumers read the published snapshot, preventing duplicate polling. Keep this producer outside the serve-loop critical path, at most one in-flight fetch with a 20-second whole-fetch deadline and the existing shared REST budget floor. It shares one fleet-level data fetch when both hosts use the same job pool; it does not independently enumerate the same repositories from both hosts every minute. The designated producer is jeff-ubuntu; the Mac obtains that structured snapshot through a read-only SSH command bounded to five seconds, with no GitHub request. Failure/rate limit/dependency host loss produces UNKNOWN with the last genuine successful timestamp; direct local outage detection continues independently. An absent SSH grant blocks starvation-observation activation but cannot suppress capacity or missing-heartbeat alerts. When any slot is IDLE and queue evidence is needed, if that data is absent, ambiguous or stale for five minutes, emit `execution-observability-unknown`; do not silently claim execution health or relabel it as starvation. Implementation must add a structured queue snapshot if the existing producer does not expose one, with eligibility=false/unknown when correlation cannot establish it.

A complete fresh Worker inventory satisfies current execution proof without consulting queue data; a complete fresh empty eligible-queue snapshot allows healthy idle. Image absence alerts even when surviving containers still execute, because replenishment is unavailable. Host-wide failures are grouped into one host event containing all affected slots and reasons. No suppression depends on slot-file occupancy, guessed churn, or a successful daemon log write.

## Timing, incidents and recovery

- Native schedule: once per 60 seconds; one invocation at a time. Probe command deadlines 3 seconds, sample total 25 seconds, HTTPS connect 5 seconds / total 10 seconds, whole invocation deadline 45 seconds. Probe only local host, with at most two concurrent Docker calls; no GitHub calls in this loop. Queue-snapshot SSH is separately bounded to five seconds inside the 45-second invocation budget.
- Confirm service down, Docker unavailable, image missing, missing/nonfunctional slot, or monitor configuration/probe failure with two consecutive fresh bad samples spanning at least 60 seconds. A recovered first miss is retained as a transient, not erased from logs. Do not wait an hour for total fleet loss.
- Confirm eligible queue starvation after five continuous minutes; stale/unknown queue observability after five minutes. Thresholds are configured contracts. Normal idle with fresh proof of no eligible queue does not page. A DOWN slot is actionable regardless of queue visibility.
- The hosted check period is 60 seconds with 120 seconds grace. An entire host/observer/network outage must transition Down within three minutes of its last accepted success heartbeat, plus provider delivery latency. Acceptance target: Slack and email receipt within five minutes of simulated failure, validated rather than assumed as a vendor SLA.
- While a threshold is pending, send a success heartbeat meaning **observer ran and no alert threshold has yet matured**, not proof of 16/16 execution. Once any threshold matures, persist the incident and delivery intent and send `/fail`; send no success until recovery. If `/fail` delivery fails, withholding success still triggers the external missing-heartbeat alert. Observer crashes before evaluating follow the same fallback.
- Recovery requires two complete fresh passing samples at least 60 seconds apart, valid config, reachable backend, present required image, all expected listeners/Workers, and no matured starvation/observability fault. UNKNOWN never clears an incident. First installation, host boot change, corrupt/missing state, or a sample gap >120 seconds requires two fresh passing samples before the first success heartbeat, even if old local state says no incident exists: the provider may have opened an outage while the observer was absent. Persist that startup/recovery gate between one-shot invocations using boot ID and last accepted sample; an ordinary scheduled process exit is not a new host outage, but a sample gap >120 seconds resets the gate. Send one success transition; Healthchecks emits recovery to both integrations.
- Persist incident generation, boot ID, last observation, pending durations, and last accepted report atomically under `~/.local/state/ezgha/fleet-monitor/`, with a process lock. Clock regressions, changed boot ID, corrupt state, and skipped ticks invalidate pending timing rather than manufacturing old duration. They cannot send a false recovery; retain a known open incident until new recovery samples.
- Persist a generation-scoped outbox intent (host, incident UUID, state transition, monotonic observation sequence) with fsync and atomic rename BEFORE each transition request. Record acceptance only AFTER response validation. On crash after send/before acknowledgement, replay the same still-current transition; never replay an older recovery after a newer fault. Reevaluate pending intents against current evidence under the same lock, retain an open incident until recovery gate passes, and discard only superseded intents with an audit record. Repeated same-state requests use provider state-transition dedup, not a false exactly-once delivery promise.
- One Down and one recovery transition per host incident under normal successful operation; network/crash replay may duplicate requests and provider delivery receipts remain authoritative. Enable hourly unresolved email reminders only with explicit account-wide scope approval at activation; Healthchecks implements this in Account Settings and it can affect checks outside this fleet. Default is reminders OFF until that account impact is approved; do not promise repeated Slack reminders unless the selected integration proves that capability. Disable indefinite maintenance suppression: any planned pause has a recorded owner and expiry, and external checks must resume automatically. No planned pause is set now.

## Delivery and security

Provision both Slack and email integrations on **each** hosted check. Default recipient is Jeffrey's verified existing operator destination; do not infer an address or channel from Git author metadata. Hosted delivery avoids requiring sendmail on either runner host. Resolve account, recipient and destination from existing authorized configuration during implementation, or record missing values as activation blockers. No account purchase, account mutation, credential rotation or test message occurs during planning.

Heartbeat URLs are secrets: keep them in macOS Keychain or a designated Linux secret store, resolved by the observer without printing them or including them in process arguments. Nonsecret monitor TOML holds credential references, host ID, service/config identity, periods and contract counts. Do not read/write `.env`, bake secrets into plists, commit them, or embed them in diagnostics. Logs and hosted payloads carry only bounded host/slot health, never tokens or raw environment/config dumps.

Use HTTPS POST and require the documented successful status plus exact stripped body `OK`. UUID ping endpoints may respond HTTP 200 with ignored `not found` or `rate limited` semantics; HTTP status alone never marks acceptance. At activation and the independent daily audit, verify via the provider Management API that both exact check UUIDs exist, are active, retain the intended period/grace and both integrations, and that accepted pings update their recorded activity. Deleted/paused checks are an external-control-plane failure, not healthy silence. Test ignored-200 variants explicitly and cap to one ping per host per minute; do not log the URL or ping key.

Delivery states are separate: local audit written, heartbeat accepted, Slack accepted, email accepted, and inbox/message receipt. A local JSONL write is never evidence of human notification. Hosted integration failure must be visible in provider diagnostics and the operational delivery check. Slack and email are both required even if one works. A credential failure must not disable the other route.

Fix the shared daemon helper separately within this implementation unit: report transport results independently; local logging cannot reset external-delivery status or suppress retry of a failed channel. Keep per-channel cooldowns and bounded commands; tests must cover Slack failure plus log success. Preserve bounded serve-loop cost rather than add synchronous retries there. Host outage detection still relies on the external observer, not this helper.

## Reuse, blast radius and limits

Do not run the existing dashboard probe's disk-container creation path, health harness canaries, image rebuild, cleanup, or watchdog from monitoring. Factor observation helpers once rather than copy the doctor parser. Current baseline was lightweight Docker calls with zero Mac containers and ten Linux containers; no full overhead benchmark was taken in planning. Deployment requires measuring a warm/loaded host: p95 sample <=25s, every invocation <=45s, at most two Docker calls concurrent, and no increase in runner restarts or lost jobs. If those constraints cannot hold, stop activation and optimize observation, not runner capacity or restart thresholds.

This design covers a provider reachable from the public internet even when the home LAN is down. It cannot guarantee delivery during simultaneous provider, Slack, and mail outages; dual channels plus a periodic delivery test expose this dependency. Configure an independent daily synthetic test check using the same integrations and verify real provider events plus actual Slack and mailbox receipts through authorized reads; fake downstream adapters only test our accounting and can never prove hosted Slack/email delivery; missing receipts remain an operational failure, never a green log-only test. Reuse provider integration tests and a scheduled check runner instead of adding an LLM cron. Do not run that daily test on the monitored runner fleet; hosting and read permissions are activation prerequisites.

## Acceptance criteria

Use deterministic fixtures first, then one final isolated real delivery drill after implementation and credentials are ready. Cover missing image, live daemon with zero containers, one missing slot, Docker hang, daemon exit, observer killed, host/network loss, simultaneous host silence, fresh idle queue, sustained eligible backlog, unknown queue, wrong config/endpoint, prefix change, one broken notification integration, corrupt/rebooted state, and recovery. Assertions must inspect per-slot evidence and provider/Slack/mail receipts using a unique incident ID; local logging or HTTP success alone never closes the test. Real host-loss cases may be simulated by disabling only a dedicated test heartbeat, never by killing production runners. Prove deployment on both native schedulers, then full real-job 6+10 per-slot execution in one final bounded acceptance run when separately authorized. Keep failed samples and receipt gaps.
