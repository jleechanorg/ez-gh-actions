# Research: CFS/NO_HZ NX panics on i9-13900K (2026-08-26)

## Executive summary

Four recent host panics have the same locally captured signature: an x86 `NX-protected page` instruction-fetch fault in PID 0 (`swapper/*`) whose stack includes `__update_blocked_fair` → `sched_balance_update_blocked_averages` → `_nohz_idle_balance` → `sched_balance_softirq`. One recurrence occurred with the Linux runner count reduced to five. That is strong evidence for a repeatable **host-kernel crash class** and evidence *against* runner count alone as a sufficient prevention; it is not proof of a Linux scheduler defect, NVIDIA defect, CPU defect, or bad RAM.

The upstream v6.17 scheduler source confirms that this is the ordinary NO_HZ idle-balance/blocked-PELT path. Upstream x86 source says the exact NX message is emitted for an instruction-fetch page fault on a present non-executable mapping. It does **not** identify who caused the invalid control flow or mapping. A proprietary/out-of-tree NVIDIA module makes the kernel tainted and materially reduces the value of a kernel-only attribution; upstream's reporting guidance explicitly asks for reproduction without third-party modules.

`nohz=off` is a supported, reversible **diagnostic containment**: it disables dyntick-idle and removes the implicated NO_HZ-idle execution route. It should be retained only as a bounded A/B discriminator while a supported kernel/firmware/hardware and NVIDIA-isolation investigation proceeds. Kernel documentation calls NO_HZ idle the normal default and documents power/idle-transition trade-offs, so this is not evidence for declaring it a durable fix.

The priority order is therefore: (1) make the next failure debuggable (one valid crashkernel reservation, kdump loaded, pstore plus off-host netconsole); (2) use `nohz=off` as immediate path-specific containment; (3) compare the supported Ubuntu `-42` kernel and a known-good rollback under otherwise identical conditions; (4) update this board's BIOS and establish Intel Default Settings in a separate maintenance boot; (5) run an untainted/NVIDIA-isolated boot; and (6) use bounded runner-load stages only as rate-modifier tests. The kernel comparison moves ahead of BIOS because it is more reversible and the Ubuntu changelog confirms a later change in the implicated idle/PELT area; this still does not make that patch the presumed cause. Do not restore the 10-runner fleet as a claim that the crash is fixed; restore/prove capacity only after the separate safety gates are satisfied.

## Scope and evidence classification

Local premise (already captured outside this note): four same-class pstore panics on `6.17.0-29-generic`, including one at runner count 5; the reported stack and `Tainted: P`/out-of-tree NVIDIA context are treated as observations, not as causal attribution.

* **Proven source fact** — directly supported by an official upstream, Ubuntu, Intel, NVIDIA, or systemd source below.
* **Inference** — a testable conclusion drawn from the local premise plus source facts.
* **Unsupported hypothesis** — plausible but not established by those facts; it must not be reported as the cause.

## Host-specific delta found during verification

Read-only checks on 2026-08-26 identify this host as an ASUS ROG MAXIMUS Z790 HERO on BIOS `3107`, running `6.17.0-29-generic` with runtime CPU microcode `0x133`, NVIDIA `595.71.05`, and taint mask `12289`. These observations change the priority of the discriminators:

* Intel's current guidance asks for microcode `0x12F` or later, so the loaded `0x133` already clears that minimum. "Update microcode" by itself is therefore not the missing intervention. Intel still recommends the latest BIOS and Intel Default Settings, and extends warranty coverage for eligible affected processors. [Intel current Vmin guidance](https://www.intel.com/content/www/us/en/support/articles/000102331/processors.html)
* ASUS now publishes BIOS `3202` (2026-08-17) for this exact board, newer than installed `3107`. ASUS says it updates Intel IPU 2026.1 microcode, memory compatibility, and ME firmware to `16.1.40.2765`; ASUS also warns that the ME update remains after a BIOS rollback. This makes `3202` a real maintenance-window variable, but not a casual or fully reversible diagnostic. [ASUS board BIOS page](https://rog.asus.com/us/motherboards/rog-maximus/rog-maximus-z790-hero-model/helpdesk_bios/)
* Ubuntu's own applied changelog confirms `6.17.0-41.41~24.04.1` incorporated upstream `sched/fair: Fix pelt clock sync when entering idle`; local APT currently offers `6.17.0-42.42+1`. Because that patch touches the idle/PELT transition but does not describe NX corruption, `-42` is a high-value supported version discriminator, not a claimed fix. [Ubuntu HWE 6.17 changelog](https://git.launchpad.net/ubuntu/+source/linux-hwe-6.17/plain/debian.hwe-6.17/changelog?h=applied/ubuntu/noble-updates) · [upstream commit](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=98c88dc8a1ace642d9021b103b28cba7b51e3abc)

If the same crash class survives current vendor BIOS/default-power settings, a supported updated kernel, and an NVIDIA-isolated boot, Intel support/warranty escalation becomes a better next step than accumulating more boot-parameter workarounds. That is an escalation threshold, not a present CPU-fault diagnosis.

## What the signature does and does not establish

### Proven source facts

* In upstream v6.17, `sched_balance_softirq()` reaches `nohz_idle_balance()`, which reaches `_nohz_idle_balance()` and `update_nohz_stats()`; the latter invokes the blocked-average update that reaches `__update_blocked_fair()`. The same named path remains in v6.19. [v6.17 `fair.c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/kernel/sched/fair.c?h=v6.17) · [v6.19 `fair.c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/kernel/sched/fair.c?h=v6.19)
* The x86 v6.17 fault reporter emits `kernel tried to execute NX-protected page - exploit attempt?` when the fault is an instruction fetch and the present page-table mapping is non-executable/NX. The text is a generic fault diagnostic, not a scheduler-specific assertion. [upstream `arch/x86/mm/fault.c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/x86/mm/fault.c?h=v6.17)
* `nohz=off` is a documented boot-time setting for disabling dynamic ticks. NO_HZ documentation describes `CONFIG_NO_HZ_IDLE` as the common default and describes periodic ticking as a special mode with power and latency/overhead trade-offs. [kernel parameters v6.17](https://www.kernel.org/doc/html/v6.17/admin-guide/kernel-parameters.html) · [NO_HZ documentation v6.17](https://docs.kernel.org/6.17/timers/no_hz.html)
* A proprietary module sets taint `P`; an externally built module sets `O`. The kernel documentation says taint can be relevant to later investigation and advises reproducing without taint. [Tainted kernels](https://docs.kernel.org/admin-guide/tainted-kernels.html) · [Reporting issues](https://docs.kernel.org/admin-guide/reporting-issues.html)
* `linux-image-6.17.0-29-generic` is Ubuntu Noble HWE package `6.17.0-29.29~24.04.1`. Ubuntu package metadata exposes newer HWE packages, but that metadata does not claim to fix this exact NX/NO_HZ signature. [Ubuntu package record](https://packages.ubuntu.com/noble-updates/amd64/linux-image-6.17.0-29-generic) · [Ubuntu 6.17.0-29 acceptance/changelog](https://lists.ubuntu.com/archives/noble-changes/2026-May/055843.html)
* Intel identifies the i9-13900K as a 13th-generation Raptor Lake desktop processor. Intel's official 13th/14th generation desktop-instability update says BIOS-delivered microcode `0x12B` addresses elevated voltage requests during idle/light activity and recommends Intel Default Settings; it does not connect that issue to this Linux stack or to NX faults. [i9-13900K specification](https://www.intel.com/content/www/us/en/products/sku/230496/intel-core-i913900k-processor-36m-cache-up-to-5-80-ghz/specifications.html) · [Intel root-cause update](https://community.intel.com/t5/Blogs/Tech-Innovation/Client/Intel-Core-13th-and-14th-Gen-Desktop-Instability-Root-Cause/post/1633239) · [Intel Raptor Lake specification update](https://edc.intel.com/content/www/us/en/design/products/platforms/details/raptor-lake-s/13th-generation-core-processor-specification-update/)
* Kdump reserves memory for a capture kernel and preserves the crashing kernel image for analysis. A panic path can enter crash capture on `die()` in PID 0/1, interrupt context, or with `panic_on_oops`. Netconsole sends kernel printk messages by UDP specifically where disk logging is unavailable. [Kdump documentation](https://docs.kernel.org/admin-guide/kdump/kdump.html) · [Netconsole documentation](https://docs.kernel.org/networking/netconsole.html)
* The kernel lockup documentation distinguishes hard lockups (no interrupt handling) from soft lockups (kernel loop without task scheduling); watchdog panic plus `panic_timeout` can reboot after detection. It is observability/recovery infrastructure, not an explanation for this captured fatal exception. [Lockup watchdog documentation](https://docs.kernel.org/admin-guide/lockup-watchdogs.html)
* NVIDIA documents both proprietary and open kernel-module flavors, recommends the open flavor on supported GPUs, and provides `nvidia-bug-report.sh` for its bug reports. That is an isolation/reporting option, not evidence NVIDIA caused this fault. [NVIDIA kernel-module documentation](https://download.nvidia.com/XFree86/Linux-x86_64/595.71.05/README/kernel_open.html) · [NVIDIA bug-report guidance](https://download.nvidia.com/XFree86/Linux-x86_64/535.98/README/addtlresources.html)
* systemd exposes CPU, memory, I/O and task resource-control settings for service/slice cgroups and reports associated accounting. Those controls can bound a VM/runner workload, but cannot make a kernel instruction-fetch fault impossible. [systemd cgroup interface](https://systemd.io/CONTROL_GROUP_INTERFACE/) · [systemd transient resource settings](https://systemd.io/TRANSIENT-SETTINGS/)

### Inferences for this incident

* The repeat stack makes the NO_HZ blocked-load path the best **execution-path discriminator**. A `nohz=off` boot is expected to avoid that route; recurrence then would substantially weaken the claim that entering the NO_HZ idle-balance path is required for this crash class.
* Recurrence at count 5 falsifies the narrow claim “ten runners are necessary for this panic.” It does not falsify runner churn, interrupt/DMA activity, VM pressure, or load shape as possible rate modifiers.
* A captured `RIP`, faulting address/CR2, page-table dump, module list, microcode revision, MCE/RAS records, and vmcore are needed before distinguishing scheduler regression/control-flow corruption from hardware/firmware/DMA/module corruption.

### Unsupported hypotheses — do not infer these

* “`__update_blocked_fair` is executing bad scheduler code” or “an upstream CFS fix exists.” No primary source found here associates this exact NX failure with that function or Ubuntu `6.17.0-29`.
* “The NVIDIA module caused the panic.” Taint makes it a mandatory isolation variable, not proof of cause.
* “The i9-13900K Vmin issue caused this Linux NX fault.” Intel's advisory makes firmware/default-power verification mandatory, but does not establish this signature.
* “RAM is healthy because no MCE/EDAC message was logged,” or conversely “this is RAM corruption.” Absence of a recorded event is not a memory test; consumer platforms may not expose ECC/EDAC evidence.
* “`nohz=off` fixed the kernel” after a short no-crash interval. It only changes a path and workload characteristics; a predefined comparison window and captured failure evidence are required.
* “Runner load caused it” or “runner load cannot affect it.” The count-5 recurrence rules out only one simplistic threshold theory.

All tests below are operator-gated maintenance work; this note changes no runtime state. First establish a baseline manifest for *every* boot: boot ID, exact kernel package/build, `/proc/cmdline`, kernel config, BIOS version, microcode revision, Intel Default Settings/power limits, DIMM profile, NVIDIA module flavor/version, taint mask, cgroup limits, runner count/churn, and off-host/local crash-capture status.

## Operational interpretation rules

1. Keep the current plan's `panic=10`/`panic_on_oops` as recovery-and-capture behavior, not prevention. Kdump must be actually loaded, not merely enabled as a service.
2. Use `nohz=off` now as the safest path-specific containment while the comparison plan is prepared, but attach an expiry/review condition: retain only if it prevents recurrence across a defined equivalent interval and the performance/power trade-off is accepted; otherwise revert after evidence collection.
3. Treat the 5-runner recurrence as a reason to stop using fleet reduction as a kernel mitigation. It remains a blast-radius/load-rate control only; the required end state is the configured 10 Linux plus 6 Mac slots with per-slot `Runner.Worker` proof.
4. Change one primary variable per boot. Combining `nohz=off`, a new BIOS, a new kernel, NVIDIA changes, and runner-count changes destroys the discriminating value of any outcome.
5. If another event occurs, preserve the raw pstore/netconsole/vmcore before rebooting or changing modules. Decode against the exact kernel's debug `vmlinux`; record RIP, CR2, error code, page tables, disassembly, taint and module addresses before assigning ownership.

This review found an upstream later scheduler/idle PELT correction — [`sched/fair: Fix pelt clock sync when entering idle`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=98c88dc8a1ace642d9021b103b28cba7b51e3abc) — but its commit message does not describe an NX instruction-fetch fault or this call chain. It is a version-comparison candidate only, not a claimed fix. No primary-source commit or Ubuntu changelog examined here explicitly associates `6.17.0-29` with this exact CFS/NO_HZ NX panic; absence of an identified fix is not proof that no downstream fix exists.
